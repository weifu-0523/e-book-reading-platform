# Plan: M4.6-fix21 — PDF 间歇性加载卡死根治（pdfrx openData → FPDF_LoadCustomDocument 死锁）

**spec**：`docs/superpowers/specs/2026-07-07-m4.6-fix21-pdf-opendata-deadlock-design.md`

---

## Goal

根治 fix19 之后残留的 ~40% 间歇性 PDF 加载卡死。三层防御（A1 主路径绕开死锁 + A2/A3 stopBackgroundWorker 重置引擎）让连续开/关 30 次成功率从 60% 提升到 ≥ 95%。

## Architecture

详见 spec 根因分析。核心改动：

```
旧（fix19 后）：
  PdfDocument.openData(_bytes!, sourceName: _uniqueSourceName)
  → pdfrx openData 把 maxSizeToCacheOnMemory 硬编码 null → 默认 1MB
  → 7-41MB PDF 走 FPDF_LoadCustomDocument + 条件变量路径
  → 重复 open/close 后条件变量死锁（PR #622 未合）
  → Future 永不 complete

新（fix21）：
  // L2: 先重置引擎（清零上一本累积的死锁状态）
  await PdfrxEntryFunctions.instance.stopBackgroundWorker();

  // L1: 强制走 FPDF_LoadMemDocument（小文件路径，无条件变量）
  _doc = await PdfDocument.openCustom(
    read: _readFromBytes,
    fileSize: _bytes!.length,
    sourceName: _uniqueSourceName,                  // fix19 唯一性保留
    maxSizeToCacheOnMemory: _bytes!.length,         // ← 关键：强制走 LoadMem 分支
  ).timeout(const Duration(seconds: 30));
```

## Tasks

### Task 1: 改 openFile 用 openCustom + maxSizeToCacheOnMemory（L1 主路径）

**Files**：`reader_engine_pdf_view/lib/pdf_renderer.dart`

**Background**：fix19 的 `PdfDocument.openData(_bytes!, sourceName: _uniqueSourceName)` 走 pdfrx `openData` → `_openData` → `openCustom`，但 `openData` 把 `maxSizeToCacheOnMemory` 硬编码为 `null`（pdfrx_pdfium.dart:638）→ 默认 1MB → >1MB PDF 走 `FPDF_LoadCustomDocument` + 条件变量死锁路径（PR #622）。改用公开 API `PdfDocument.openCustom` 直接传 `maxSizeToCacheOnMemory: _bytes.length`，强制 pdfrx 走 `if (fileSize <= maxSizeToCacheOnMemory)` 分支 → `FPDF_LoadMemDocument`（一次性载入 pdfium 堆，无条件变量）。

**Steps**：
- [x] 在 `openFile` 内、`_uniqueSourceName` 赋值之后、原 `PdfDocument.openData(...)` 调用处，替换为 `PdfDocument.openCustom(...)` 调用
- [x] 实现 read callback `_readFromBytes`：仿 pdfrx `_openData` 内部实现（pdfrx_pdfium.dart:679-688），从 `_bytes` 拷贝到 native buffer
- [x] 传 `fileSize: _bytes!.length`、`sourceName: sourceName`（局部非空别名）、`maxSizeToCacheOnMemory: _bytes!.length`
- [x] 加 `pdfDiagLog('openFile path=openCustom (LoadMemDocument), fileSize=${_bytes!.length}')` 日志（SC3）
- [x] 大文件回退：`if (_bytes!.length > 200 * 1024 * 1024)` 时回退到旧 `openData` 路径 + 日志告警（SC5，A1 防御）
- [x] 更新 `openFile` 的 dartdoc 注释，说明为何用 openCustom 而非 openData（指向 PR #622 + spec）
- [x] TimeoutException 错误信息追加 "已尝试 LoadMemDocument 路径 + stopBackgroundWorker 重置仍超时"

### Task 2: openFile 前调 stopBackgroundWorker（L2 引擎重置）

**Files**：`reader_engine_pdf_view/lib/pdf_renderer.dart`

**Background**：pdfrx `BackgroundWorker._instance` 是单例 isolate（worker.dart:17），所有 pdfium 调用串行化在里面。重复 open/close cycle 后 isolate 状态可能进入死锁边缘。`PdfrxEntryFunctions.instance.stopBackgroundWorker()`（pdfrx_entry_functions.dart:61）调 `_deinit()` → `FPDF_DestroyLibrary` + kill isolate，下次 `BackgroundWorker.compute` 自动 `_ensureInit` 重建干净 isolate。espresso3389 在 issue #184/#430 官方推荐此 API 释放 pdfium 堆 + 重置状态。

**实现调整（vs 原 plan）**：`_resetPdfrxEngine()` 调用位置从"openFile 最开头"改到"`File.readAsBytes` 成功之后、`openCustom` 之前"。原因：避免文件不存在等 early-fail 路径白白触发 native 调用（pdf_renderer_test.dart 的 `openFile missing file` 测试在这条路径上）；L2 的目标"openCustom 跑在干净 isolate 上"仍然满足。

**Steps**：
- [x] 在 `openFile` 内 `readAsBytes` 成功之后、`openCustom` 之前，加 `await _resetPdfrxEngine()` 调用
- [x] 新增私有方法 `Future<void> _resetPdfrxEngine()`（5s timeout + try/catch，失败仅日志不阻塞）
- [x] `import 'package:pdfrx/pdfrx.dart'` 已存在，PdfrxEntryFunctions 通过 `export 'package:pdfrx_engine/pdfrx_engine.dart'` 暴露（已验证无需新增 import）
- [x] 在 dartdoc 里说明：为何 openFile 前要重置（清零累积死锁状态，A2 防御）

**Verification**：
- [x] dart analyze 通过
- [ ] 日志每次 openFile 前有 `stopBackgroundWorker: start` / `done`（SC4，待用户端到端测）

## Risks & Mitigation

| Risk | 缓解 |
|------|------|
| `stopBackgroundWorker` 自身在 isolate 已死锁时卡 | Task 2/3 都加 5s timeout + try/catch，失败仅日志不阻塞主流程 |
| `openCustom` read callback 跨 isolate 访问 `_bytes` 不安全 | 与 pdfrx `openData` 内部实现一致（`_openData` 也是这么调 openCustom），不存在新风险 |
| >200MB PDF 走回退路径仍可能卡死 | 极罕见场景（电子书很少有 >200MB PDF），日志告警，用户重启进程兜底（与现状相同） |
| 改动后 fix19 sourceName 唯一性失效 | openCustom 接受 sourceName 参数，行为一致（SC8 验证） |
| pdfium LoadMemDocument 对 41MB PDF 堆压力 | LoadMemDocument 是 pdfium 稳定 API，小文件一直走这条；41MB 在 pdfium 堆承受范围内 |
