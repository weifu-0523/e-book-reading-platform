## Executive Summary

The M1.5b+c milestone lands a coherent, well-structured batch-preprocess + same-book Q&A feature across 13 new files and ~10 modified files. Architecture matches the spec: `BookChunker` is a pure function, `BookPreprocessor` is a clean 2-phase state machine with circuit breaker and skipIfRunning, and `BookQaService` is a textbook pipeline (history short-circuit → key check → FTS → prompt → stream → parse → persist). The DAO/Service/Controller/Widget layering is faithful to the M1.5a precedent. Schema migration is correct (both onCreate and onUpgrade build the new tables + FTS5 + indices). i18n, AGPLv3 hygiene, and the explicit "no cost/token UI" constraint (memory `feedback_no_cost_estimation`) are all respected — no API keys are logged, no `print()` statements remain.

The implementation is **production-ready with one critical fix and several important follow-ups**. The critical issue is a `TapGestureRecognizer` memory leak in `QaAnswerView` (stateless widget creates new recognizers per build; during streaming this multiplies rapidly). Important issues include the `chapterCountFor` linear-probe performance cliff for large EPUBs (each iteration re-parses the file), the `failedChapters` field being permanently empty (deviation from spec §7.1 which wanted per-chapter failure surfacing), and a TOC drawer marker policy that only renders ✓ after `done` rather than per-chapter during chunking. Test coverage is solid (~60 new meaningful tests across 13 files; total 659 passing at concurrency=1).

The work is shippable as `v0.9.0-alpha` (already tagged and pushed). Recommend landing the critical recognizer fix in a point release before broad user exposure to long Q&A sessions.

## Code Quality Findings

### Critical (must fix before release)

#### C1 — `TapGestureRecognizer` memory leak in `qa_citation_spans.dart` / `qa_answer_view.dart`
**Files**: `app/lib/features/ai/widgets/qa_citation_spans.dart:28-30` + `app/lib/features/ai/widgets/qa_answer_view.dart:13-42`

`buildQaCitationSpans` instantiates a fresh `TapGestureRecognizer()` for every `CitationSegment`, and `QaAnswerView` (a `StatelessWidget`) calls it on every `build()`. The framework does NOT auto-dispose recognizers attached to `TextSpan.recognizer` — this is a well-documented Flutter leak ([Stack Overflow #48914775](https://stackoverflow.com/questions/48914775)). During streaming, every `QaChunkEvent` triggers a rebuild, so a 50-citation answer streamed over 200 chunks can leak ~10,000 un-disposed recognizer objects holding closure references to `onCitationTap`.

**Fix**: Convert `QaAnswerView` to `StatefulWidget`. In `initState`, build the segment list + recognizers once. Hold recognizer references in a `List<TapGestureRecognizer>` field. In `dispose`, call `.dispose()` on each. Rebuild only the `RichText` text content via `setState`, OR rebuild spans only when the segment count changes (cheap to detect).

### Important (should fix soon)

#### I1 — `chapterCountFor` linear-probe re-parses EPUB file N times
**File**: `app/lib/core/app_providers.dart:46-58`

```dart
chapterCountFor: (book) async {
  final provider = book.format == BookFormat.epub
      ? EpubChapterTextProvider()
      : PdfChapterTextProvider();
  var count = 0;
  while (await provider.get(book.filePath, count) != null) {
    count++;
    if (count > 10000) break;
  }
  return count;
},
```

For a 200-chapter EPUB this loop calls `provider.get()` 201 times, and each call re-reads + re-parses the EPUB spine (the inline comment admits this is O(N) file reads). A user importing a thick book on a slow SD card will see seconds of UI blocking before chunking even starts. Worse, this runs on the import-completion path which is on the UI isolate.

**Fix**: Add a `count(filePath)` method to `EpubChapterTextProvider` that reads the spine length once. The PdfChapterTextProvider already knows page count cheaply. Drop the linear probe entirely. (CHANGELOG already flags this as deferred — escalate priority.)

#### I2 — `failedChapters` is always empty; spec §7.1 "进度条 23/45 (2 章失败)" not delivered
**Files**: `app/lib/services/ai/book_preprocessor.dart:127` + `:196-202`

The preprocessor emits `PreprocessDoneEvent(const [])` unconditionally — the per-chapter `failed` list built up in `_phase2Summarize` is never threaded back to the Done event. Furthermore, `PreprocessChapterFailedEvent` is declared (line 32) and pattern-matched in the controller (line 121), but **never instantiated** anywhere — pure dead code.

**Fix**: Track `failed` list across `_phase2Summarize`, then pass to `PreprocessDoneEvent(failed)` at the end. Emit `PreprocessChapterFailedEvent(i, error)` on transient failures before continuing. The controller already routes these correctly. The BookDetailPage "N 章预处理失败" UI is already wired — it just never sees non-empty `failedChapters` today.

#### I3 — §7.3 stream stall / total timeout not implemented
**File**: `app/lib/services/ai/book_qa_service.dart:142-148` + `app/lib/services/ai/open_ai_compatible_client.dart:77-91`

`OpenAiCompatibleClient.streamChat` has a 30s timeout only on `send()` (the initial HTTP request). Once streaming begins, there is no per-chunk stall detection — if the LLM sends one chunk then hangs, the user waits forever. Spec §7.3 explicitly wanted ">30s between chunks → timeout" and "total 90s → cancel". The QaAskDialog has no "停止" button either.

**Fix**: Wrap the `await for` loop in `BookQaService.ask` with a per-chunk `Future.delayed` race using a `Timer` that resets each iteration, throwing `AiNetworkException('stalled')` on expiry. Add a stop button to `QaAskDialog` that calls `qaControllerProvider(...).notifier.reset()` (cancels the subscription).

#### I4 — §5.3 "预处理进行中, 回答可能不全" hint not implemented
**Files**: `app/lib/features/ai/widgets/qa_ask_dialog.dart` + `app/lib/features/ai/providers/qa_controller.dart`

Spec §5.3 wanted a small-text warning when Q&A is asked while preprocessing is still running. The QaController does not watch `bookPreprocessControllerProvider`, so the dialog cannot know. Currently a user asking mid-preprocess gets a partial answer with no signal that more chapters are coming.

**Fix**: In `QaAskDialog._buildBody`, when `state.status == streaming/done`, also `ref.watch(bookPreprocessControllerProvider(widget.bookId))` and show a small caption "预处理进行中 (N/M)" when that controller is `chunking`/`summarizing`. Cheap one-line addition.

#### I5 — Q&A history UI (§9.3) not delivered
**Files**: `app/lib/features/ai/widgets/qa_ask_dialog.dart` + `app/lib/features/ai/providers/qa_controller.dart:106-108`

`QaController.setHistory` exists but is never invoked; `QaAskDialog` renders no history list; long-press delete (§9.3) is missing. The acceptance criterion §14 "Q&A 历史可查看 + 重发" is not met. The DAO and controller infrastructure is built — only the widget wiring is missing.

**Fix**: In `QaAskDialog.initState`, `ref.read(qaHistoryDaoProvider).getByBook(widget.bookId, limit: 5)` then `qaControllerProvider(...).notifier.setHistory(rows)`. Render a horizontal list above the input field. On tap, populate `_controller.text` and `_submit()`. On long-press, call `deleteEntry` and refresh.

### Minor / Style

#### M1 — TOC drawer markers only render at status==done
**File**: `app/lib/features/reader/widgets/toc_drawer.dart:81-83`

`_buildMarker` returns null unless `state.status == PreprocessStatus.done`. Spec §5.1 implies ✓ marks should appear progressively as chapters are chunked. Current behavior: nothing during chunking/summarizing, then ✓ on all non-failed chapters at once when done. Not wrong, but less informative than spec intended. Acceptable trade-off if implementing per-chapter querying is too costly.

#### M2 — `BookDetailPage._retryWithBookLookup` duplicates `LibraryPage.handleImportResult` Book reconstruction
**Files**: `app/lib/features/library/pages/book_detail_page.dart:312-331` + `app/lib/features/library/pages/library_page.dart:43-76`

Both sites manually reconstruct `Book` from a drift row with the same 11-field mapping. If `Book` gains a field, both must be updated. Suggest extracting a static `Book.fromRow(BooksCompanion row)` or `Book.fromDrift(BookData row)` helper in `data/models/book.dart`.

#### M3 — BookDetailPage uses Chinese strings instead of i18n keys
**File**: `app/lib/features/library/pages/book_detail_page.dart:218-350`

The `_PreprocessPanel` widget hard-codes Chinese strings ("AI 预处理：未开始", "切分章节中", "取消", "API key 无效", "去设置", "重新预处理", "失败", etc.). Other M1.5bc UI files correctly use `AppLocalizations`. This is inconsistent with the project's i18n policy and breaks the EN locale. (Acceptance §14 mentions i18n completion as a polish item.)

#### M4 — `_QaClientAdapter` creates new HTTP client per request
**File**: `app/lib/core/app_providers.dart:91-98`

Every `BookQaService.ask()` call constructs a new `OpenAiCompatibleClient` which in turn constructs a new `http.Client()`. Connection pooling is lost. Not a correctness bug, but per-request TCP handshake overhead. Consider passing a shared `http.Client` from the provider.

#### M5 — `bookPreprocessControllerProvider` has a default `_NoOpBookPreprocessor` rather than `throw UnimplementedError`
**File**: `app/lib/features/ai/providers/book_preprocess_controller.dart:150-153`

The plan (§4.4) specified `throw UnimplementedError('Override in ProviderScope')` to mirror `qaControllerProvider`'s pattern. The implementer chose an inert default instead. The stated rationale (widget tests don't need to override) is reasonable, but the divergence from `qaControllerProvider` (which still throws) creates an inconsistency: a production code path that forgets to wire the override would silently never preprocess instead of failing loudly. Either both should throw or both should default — pick one.

#### M6 — `_phase2Summarize` does not skip chapters already in `ai_summaries` cache
**File**: `app/lib/services/ai/book_preprocessor.dart:158-209`

Spec §4.3 said "resume 时检查 ai_summaries cache, 已生成的章跳过". The implementation relies entirely on AiGuide's internal cache lookup (which is correct in principle) but the preprocessor itself unconditionally calls `aiGuide.run(...)` for every chapter. If AiGuide's cache lookup is ever moved or its key changes, this will silently re-bill the LLM. Adding a defensive `aiSummariesDao.findBySourceHash(...)` check would be belt-and-suspenders. Acceptable as-is since AiGuide's cache contract is documented.

#### M7 — `analyze` reports 180 info-level lints
Most are pre-existing `prefer_const_constructors` / `cascade_invocations` in test files. No warnings or errors in production M1.5bc code. Acceptance criterion "dart analyze 无 warning" is technically met (info ≠ warning) but worth a cleanup pass.

## Verdict

**Ship with follow-ups.**

The critical `TapGestureRecognizer` leak (C1) should be fixed in a point release (e.g. `v0.9.1-alpha`) before users hit long Q&A sessions. The milestone is otherwise production-ready: schema is correct, the state machine is sound, security is clean, and the user-visible feature works end-to-end. Important spec deviations (Q&A history UI §9.3, per-chapter failure surfacing §7.1, stream stall timeout §7.3, in-progress warning §5.3) should be scheduled for M2.0c.

The existing tags (`m1.5bc-complete`, `v0.9.0-alpha`) on Gitee are appropriate given the spec's acceptance criteria are 90%+ met and the missing items are UX polish rather than correctness bugs.

3. **I2** (M2.0c): Thread `failed` list into `PreprocessDoneEvent`; emit `PreprocessChapterFailedEvent` on transient errors. Surfaces "N 章预处理失败" honestly and enables per-chapter retry.
4. **I5** (M2.0c): Wire `QaController.setHistory` from `QaAskDialog.initState`; render history list per §9.3. Closes the acceptance criterion gap.
5. **I3** (M2.0c): Add per-chunk stall detection + total 90s cap + "停止" button in QaAskDialog per §7.3.
6. **I4** (M2.0c): Show "预处理进行中" caption in QaAskDialog when preprocess controller is active per §5.3.
7. **M3** (M2.0c): Replace hard-coded Chinese strings in `_PreprocessPanel` with `AppLocalizations` keys.
8. **M5** (M2.0c): Decide consistency policy for family providers — either both `bookPreprocessControllerProvider` and `qaControllerProvider` throw by default, or both use inert defaults.
