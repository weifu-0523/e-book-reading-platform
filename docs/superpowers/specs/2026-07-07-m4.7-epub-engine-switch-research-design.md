## 1. Context（为什么做这份调研）

### 1.1 背景：fwfh 路线已死

M4.6-fix20 已在 `reader_engine_epub_view` 上烧了 7 轮（fix12→17 + 本 session 的 Solution A 整页测量 + Solution B 渲染层兜底），全部失败。根因经逐字测试锁定：

```
measurer 单段独立渲染高度: 81.0 px
整页实际渲染高度:         128.0 px
drift:                    -47.0 px（58% undercount）
```

fwfh 0.15.3 没有任何官方测量 API，单段独立测量 ≠ 整页实际渲染高度，永远存在 drift → 用户看到的"末段被吃掉"现象无法在该库上根治。

### 1.2 fwfh 上游确认（issue #138）

[fwfh issue #138](https://github.com/daohoangson/flutter_widget_from_html/issues/138)（2020-03 开至今 Open、标 `help wanted`、无人接手）中，作者 daohoangson 明确表示不知道如何做分页。社区开发者 getBoolean 总结的死结：

> *"The crux of the problem is that we need to know the height of the widget **before it is rendered**, but this is inherently orthogonal to Flutter's layout system."*

**结论**：升级 fwfh 0.16+ 也不会解决（架构性缺陷，非版本 bug）。继续在 fwfh 上投资是沉没成本。

### 1.3 本调研目标

在彻底放弃 fwfh 路线之后，需要回答两个问题：

1. **业界开源 EPUB 阅读器都用什么技术栈？分页机制是什么？**
2. **体验被公认优秀的 Neat Reader 是怎么搭的？我们能借鉴什么？**

回答这两个问题，给下一轮 EPUB 引擎切换提供工程化、有据可查的决策依据。

## 3. 开源 EPUB 阅读器全景（按渲染引擎分类）

### 3.1 类别 A：WebView + CSS columns（工业级正解）

| 项目 | 栈 | 分页机制 |
|---|---|---|
| **epub.js**（futurepress，BSD） | 纯 JS | `column-width` CSS + 单 iframe 横向 translateX，浏览器原生 `break-inside: avoid` 自动不切行 |
| **Readium CSS / R2 Navigator** | JS/TS | 同样用 CSS columns（明确拒绝 `overflow: paged-x`，因为浏览器支持差） |
| **foliate-js**（Foliate 桌面用） | JS | 同上，轻量化 |
| **flutter_epub_viewer**（fayis672，30👍） | Flutter + `flutter_inappwebview` + epub.js | 把 epub.js 装进 inappwebview，CFI 定位、文本选择、高亮全保留 |
| **FlafyDev/epub_reader**（126★） | Flutter + 自带 webview 渲染器 | 同思路，Flutter 壳 + JS 渲染器 |
| **vocsy_epub_viewer**（98👍） | Flutter plugin | 封装 **Folioreader**（iOS Swift / Android Java 原生），同样是 WebView 系 |

**共同点**：让浏览器排版引擎做分页。浏览器对 `column-width: <pageWidth>; column-fill: auto; height: <pageHeight>` 的支持是工业级成熟的，**永远不会出现"末行被切掉一半"**。

**官方文档背书**：[R2 Navigator Design Dilemmas](https://readium.org/technical/r2-navigator-design-dilemmas) 明确说"推荐 CSS columns for both web and mobile reader, for consistent rendering of pagination"。

### 3.2 类别 B：原生 TextPainter 自绘（轻量、可定制）

| 项目 | 栈 | 分页机制 |
|---|---|---|
| **cosmos_epub 1.0.0**（44👍，2026-04 最新） | Flutter 原生 | HTML→TextSpan 自建转换器（HtmlTextBuilder），TextPainter 真实量高再切页。**已抛弃 flutter_html** |
| **epub_view**（161👍 但维护 Poor） | Flutter + dart-epub | 用 fwfh 渲染，分页能力弱（和我们的坑同源） |
| **Ferrous**（JuanSoFly） | Dart `epubx` + `flutter_html` | Rust 只做 PDF；**EPUB 仍是 Dart 原生 HTML 渲染，分页问题没解决** |

**关键证据**：cosmos_epub 1.0.0 changelog 是最重要的可参考案例——他们**已经走过和我们一模一样的路并已成功脱困**：

> *"Replaced flutter_html with native `Text.rich`/`SelectableText.rich` for full control over text layout...*
> *Accurate Pagination: TextPainter-based page splitting with real font metrics instead of height estimation. **Pages are consistent in height.**"*

也就是说：**抛弃 fwfh / flutter_html，改用 `Text.rich` + `TextPainter` 真实分页** = 这条路被验证过。

### 3.3 类别 C：原生排版引擎（最专业、移植成本最高）

| 项目 | 栈 | 分页机制 |
|---|---|---|
| **KOReader / crengine**（C++） | Lua + C++（crengine for EPUB，mupdf for PDF） | 自有排版引擎，逐行排版时记录可分页点；crengine 是 Calibre/FBReader 都用的老牌引擎 |
| **FBReader / ZLibrary** | C++/Java | **字符计数估算**（默认 2048 字节/页），不精确但够用 |
| **FolioReader**（vocsy 底层） | iOS ObjC / Android Java | WebView 系 |

### 3.4 类别 D：Flutter + Rust（新兴，但 EPUB 部分仍走 Dart）

| 项目 | EPUB 部分 | 说明 |
|---|---|---|
| **Ferrous**（JuanSoFly） | Dart `epubx` + `flutter_html` | Rust 只做 PDF（pdfium-render）和文件扫描；**EPUB 仍是 Dart 原生 HTML 渲染，分页问题没解决** |
| **velora**（blueokanna） | Rust 核心 + flutter_rust_bridge | Rust 处理 MOBI/AZW3/TXT 解码；EPUB 渲染仍是 Flutter 侧 |

**结论**：Rust 桥对**文本解码/图像处理**有用，但**对 HTML 分页精度无帮助**——因为分页是 Flutter widget 层的问题，Rust 替代不了 Flutter 的 layout 系统。我们项目不需要走这条路。

## 4. Neat Reader 拆解（用户特别指定参考对象）

### 4.1 决定性证据：包名暴露底层架构

商业版 Neat Reader 的 Android 包名是 **`com.gzhi.neatreader.r2.main`**（[Google Play](https://play.google.com/store/apps/details?id=com.gzhi.neatreader.r2.main&hl=zh_CN)）。这个 `.r2.` 不是随便命名的——它直接对应 **Readium R2**（Readium 第二代架构）。这是判断 Neat Reader 技术栈的钥匙。

进一步佐证：
- 官网自称 *"a powerful kernel"*、*"robust parsing engine perfectly supports ePub 2 and most ePub 3 standards"* —— Readium 引擎的典型宣传话术
- 跨平台一致性极强（Win / Mac / iOS / Android / Web / Kindle Fire）—— Readium "全家桶"策略的产物

### 4.2 Neat Reader 真实架构：Readium 全家桶

| 端 | 渲染层（核心） | 语言/框架 |
|---|---|---|
| **iOS / iPadOS** | [`readium/swift-toolkit`](https://github.com/readium/swift-toolkit)（`R2Navigator`）| Swift + UIKit/WebKit |
| **Android** | [`readium/kotlin-toolkit`](https://github.com/readium/kotlin-toolkit)（`r2-navigator-kotlin`）| Kotlin + Android WebView |
| **Windows / macOS** | Readium Desktop（`r2-navigator-js`）| Electron + TypeScript |
| **Web 端**（Open Web App）| `r2-navigator-js` | 纯浏览器 |
| **后端云服务**（10GB 同步）| 未公开，推断为 Node/Go/Java | 自研 |

### 4.3 各端 navigator 共享的"骨架"

- **`Publication` 模型**：所有端都用同一个 JSON-LD 数据结构描述一本书（manifest、spine、TOC、page-list）
- **`Locator`（CFI）**：阅读位置、高亮、笔记用统一的 Locator JSON 表示 → 这是实现"任意端读到第 N 页、任意端高亮"的基础
- **DRM 可选挂 LCP**（Neat Reader 没用，因为是消费级）

### 4.4 为什么 Neat Reader 体验好（关键：分页机制）

Readium 全平台 navigator 的分页机制**完全一致**：

```
EPUB 一章 XHTML → iframe 加载 → 注入 CSS:
   column-width: <viewportWidth>;
   column-gap: <gap>;
   height: <viewportHeight>;
   column-fill: auto;
→ 浏览器排版引擎自动把内容铺成横向 N 列
→ 翻页 = 横向 translateX 一列宽
```

这套方案的关键性质：
1. **永不切行**：浏览器原生的 `break-inside: avoid` / `break-before` / `break-after` 工业级成熟，文字行永远不会被腰斩
2. **像素精确**：列宽 = 视口宽，列高 = 视口高，不存在我们项目 -47px drift 那种估算误差
3. **响应式**：窗口/字号一改，重新计算 column 数量即可，立刻重排
4. **CFI 精确定位**：用 DOM Range → CFI 字符串记录位置，跨端跨字号都能定位到同一处

这和"方案 1：WebView + epub.js（CSS columns）"是**同一种技术路线**——epub.js 和 Readium 在分页机制上完全一致，区别只在数据模型和 API 设计。

### 4.5 配套服务架构（云同步）

商业版 Neat Reader 的服务端栈未公开，但从行为反推：

| 服务 | 推断 |
|---|---|
| 用户系统 / VIP | 自研后端（REST API + JWT） |
| 10GB 云存储 | 对象存储（S3/OSS 类）+ 元数据 DB |
| 阅读数据同步 | 上传 EPUB → 服务器解析 manifest → 客户端拉 Locator 增量同步 |
| 客户端缓存 | 各端 navigator 自带本地缓存（IndexedDB / SQLite / UserDefaults） |

商业模式：**免费本地读 + 付费云同步**（10GB / VIP）。这是消费级阅读器的标准打法。

### 4.6 第三方仿制品（顺带，但不是同一个东西）

搜索过程中出现的 [`SailRuo/Neat-Reader`](https://github.com/SailRuo/Neat-Reader)（个人 0 star 项目，2026-02 才开始）是**第三方仿制品**，和商业版完全不同：

| 层 | 技术 |
|---|---|
| 前端 | Vue 3 + TypeScript + Pinia + Vite |
| 阅读引擎 | **epub.js / foliate-js** + pdfjs-dist |
| 桌面壳 | 早期 Electron，2026-03 迁移到 **Tauri**（Rust 主进程 + PyInstaller sidecar Python 后端） |
| 本地存储 | IndexedDB（localforage） |
| 特色功能 | 集成千问 AI、百度网盘、node-edge-tts |

虽然这是仿制品，但**它选 epub.js + CSS columns 这件事本身就是社区共识的佐证**：在 Web/桌面端做 EPUB 阅读，主流路线就是 CSS columns。它从 Electron 迁到 Tauri 也是值得参考的信号——安装包 2.5MB vs 85MB。

## 5. 方案对比与决策（Architecture Decisions）

### 5.1 候选方案全景

| 方案 | 技术栈 | 分页精度 | 工作量 | 桌面支持 | 维护风险 |
|---|---|---|---|---|---|
| **A1：WebView + epub.js**（`flutter_inappwebview`）| Flutter 壳 + epub.js | ⭐⭐⭐⭐⭐ 工业级 | 小（pub 包开箱）| WebView2 / WKWebView / WebKitGTK 均支持 | 中（依赖 inappwebview 桌面成熟度）|
| **A2：参考 cosmos_epub 自研 TextPainter 分页** | Flutter 原生 `Text.rich` | ⭐⭐⭐⭐ 像素精确 | 中（HTML→TextSpan 转换器）| 完美（纯 Flutter）| 低 |
| A3：升级 fwfh 0.16+ | fwfh | ❌ 不可行（架构缺陷）| — | — | 高 |
| A4：Flutter + Rust 桥（如 Ferrous/velora）| flutter_rust_bridge | 不解决分页问题 | 大 | 完美 | 高 |
| A5：纯自绘 CustomPaint + TextPainter | CustomPaint | ⭐⭐⭐⭐ | 大（过度工程）| 完美 | 中 |

### 5.2 A1 vs A2 详细对比

**A1：WebView + epub.js**

优势：
- 工业级稳定，Neat Reader / Readium / foliate-js / vocsy 全走这条路
- 自带 CFI 定位、高亮、搜索、字体缩放、RTL、重排
- `flutter_epub_viewer`（fayis672）开箱即用
- 上次 session 我们在 fwfh 上烧了 7 轮失败，根源就是 Flutter 原生 layout 系统无法事前测高——WebView 路线直接绕过这个死结

代价：
- 放弃原生 Flutter 渲染（外观更像"嵌入式网页"）
- 内存 ~30-50MB 多一个 WebView 进程
- 需要 JS↔Dart bridge（CFI ↔ 智阅 Locator 互转）
- **桌面端（Windows）的 WebView2 支持需验证**——`flutter_inappwebview` 在 Windows 上要额外配置，且这是项目首次引入 WebView

**A2：参考 cosmos_epub 重写渲染层**

优势：
- 保持 Flutter 原生体验，性能好，内存轻
- 可继承我们现有的字体注入（LXGWNeoXiHei）
- 可继续复用 epubx 解析层、TypographyStyleInjector
- 对纯文字 + 少量图片的 EPUB（我们的核心场景：金融/教材类）完全够用
- cosmos_epub 是 BSD-3，可参考/借用源码

代价：
- HTML→TextSpan 转换器工作量中等
- 富 HTML（嵌套表格、SVG、视频）支持度不如 WebView
- 图片、表格、SVG 要单独处理

### 5.3 决策记录

#### AD1（推荐）：**首选 A1（WebView + epub.js），备选 A2（TextPainter 自绘）**

**推荐 A1 的理由**：

1. **证据强度**：Neat Reader / Readium / epub.js / foliate-js / vocsy 全行业走 CSS columns，已验证。cosmos_epub 是孤证（虽然有），A1 是工业级共识。
2. **绕过死结**：上次 7 轮失败的根源是 Flutter layout 系统无法事前测高。A1 让浏览器引擎做排版，直接绕过这个死结，不是"换个库再试一次"。
3. **生态完整**：epub.js 自带 CFI（Canonical Fragment Identifier）——我们已经做了 M3.3 precise locator，CFI 是同源标准，可平滑对接。
4. **桌面支持虽需验证，但有路径**：`flutter_inappwebview` 在 Windows 上用 WebView2（和 Tauri 同款），不是死路。

**保留 A2 作为备选的场景**：
- 如果 A1 在 Windows 桌面端 WebView2 不可用 / 性能不能接受
- 或者发现 epub.js 对我们特定 EPUB（中文 CJK 排版、字体嵌入）支持不好
- 则降级到 A2，参考 cosmos_epub 重写

#### AD2：明确放弃的方向

- ❌ **不升级 fwfh**（issue #138 证明上游无能力）
- ❌ **不上 Rust 桥**（不解决分页问题）
- ❌ **不做纯自绘 CustomPaint**（cosmos_epub 已证明 `Text.rich` 就够，CustomPaint 是过度工程）

## 6. Risks（风险与防御）

### R1：A1 桌面端 WebView2 风险

- **风险**：`flutter_inappwebview` 在 Windows 上需要 WebView2 runtime，部分老旧系统可能未安装。
- **影响**：可能导致桌面端首次启动失败或需要额外引导安装。
- **防御**：M4.8 plan 的 Pre-flight Checklist 第一项就是"验证 `flutter_inappwebview` 在 Windows 11 上的可用性 + WebView2 bundling 策略"。如不可行，立即切到 A2。

### R2：A1 内存增加

- **风险**：WebView 进程额外 ~30-50MB 内存。
- **影响**：低端设备（手机端）可能 OOM。
- **防御**：智阅目前主战场是桌面 + iPad，手机端不是 P0。如未来要做手机端，再评估。

### R3：CFI ↔ 智阅 Locator 互转

- **风险**：epub.js 用 CFI（DOM Range），智阅现有 Locator 是 (chapterIndex, charOffset)。互转需要适配层。
- **影响**：迁移期间高亮/笔记数据可能需要 migration。
- **防御**：M4.8 plan 必须包含 Locator 适配层设计 + 数据 migration 脚本（参考 M2.0b sync-conflict 的迁移思路）。

### R4：A2 路线如果触发时的成本

- **风险**：A1 在桌面验证失败 → 切 A2，但 A2 的 HTML→TextSpan 转换器覆盖度未知。
- **影响**：可能延期。
- **防御**：M4.8 plan 阶段就预先 spike A2 的 HtmlTextBuilder 原型（1-2 天），作为 fallback 保险。

### R5：富 HTML 支持降级

- **风险**：无论 A1 还是 A2，对复杂表格/SVG/视频的支持都不如原生 fwfh（虽然 fwfh 分页烂，但 HTML 渲染覆盖度高）。
- **影响**：极少数富媒体 EPUB 可能显示不全。
- **防御**：智阅当前书库以纯文字金融/教材为主，可接受。如未来需要，再单独处理。
