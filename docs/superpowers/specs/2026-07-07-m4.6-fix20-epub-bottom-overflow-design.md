# M4.6-fix20 — EPUB 底部文字溢出根治（整页测量重写）

**日期**：2026-07-07
**类型**：bugfix（架构层）
**前置**：M4.6-fix10/12/13/15/16/17（5 轮同类失败，详见下文根因）

---

## Context（为什么做）

用户报告：EPUB 格式电子书在阅读区**底部经常有溢出问题**，部分文字在底部溢出后看不到。

附截图（用户实测）：纯文字章节（财务报表主题），最后一行"...公司的所有者或者说股东把钱投放到公司来；同时，作为存续经营的企"——句子明显没说完就被截断，文字直接消失在阅读区底边。

这是 **fix12 → fix13 → fix15 → fix16 → fix17 共 5 轮修复后的回归**。每一轮都声称"根治溢出"，但用户每次都报还溢出。按 systematic-debugging Phase 4.5「3+ 次失败 = 质疑架构」原则，本轮不再调公式，直接从架构层重写。

---

## 根因分析（含现场证据）

### 证据 1：历史 5 轮失败链

| fix | 改动 | 声称 | 用户实测 |
|---|---|---|---|
| fix12 | `ClipRect` 裁切 | 防溢出 | "丢一大段内容"，回退 |
| fix13 | 回退 ClipRect + measureHeight -2.5 行 | 保守测量 | 仍溢出 |
| fix15 | paginator 加图片高度估算 | 补图片 drift | 仍溢出 |
| fix16 | `paginateFromActualHeights` + fwfh 实测 | 双测量系统合一 | 仍溢出 |
| fix17 | measurer 注入首行缩进 EM SPACE | 补缩进 drift | 仍溢出 |

**共同盲区**：5 轮都在调"单段测量公式精度"，没意识到 drift 本质是 fwfh **单段独立渲染 vs 整页一次渲染的上下文差异**。

### 证据 2：widget test 复现（drift 量化）

test/debug/epub_drift_measure_test.dart 实测同一段 HTML：

```
=== (a) measurer 独立渲染高度: 81.0 ===
=== (b) 完整链路: PageView=800x600, maxRichTextBottom=200.0 ===
=== (b) 实际内容渲染高度（top72 → maxBottom）: 128.0 ===
=== drift: measurer=81.0, actual=128.0, delta=-47.0 ===
```

**drift = -47px（measurer 少算 58%）**。单段独立测量 81px，整页一次渲染时该段实际占 128px。

### 证据 3：drift 方向解释了两个看似矛盾的现象

- **大多数页"未填满"**（widget test 实测 fill 20%-74%）：因为 paginator 把段间距/缩进累加进去，但 fwfh 整页渲染时段间距会与下一段首行有 baseline 重叠，实际占位 < 单段测量累加。所以 paginator 以为"这页满了"实际只填了一半。
- **特定页"溢出"**（用户报的底部文字看不到）：当某页刚好卡在边界——段落累积的「单段测量和」刚好 < slot 高度（paginator 觉得塞得下），但「整页实际渲染」> slot 高度 → 溢出。47px drift 相当于约 1.5 行文字，正好对应"最后一行半被裁"。

### drift 的 fwfh 内部原因（推测，无 fwfh 源码证据但行为可观测）

`flutter_widget_from_html` 对单个 `<p>` 和对包含多个 `<p>` 的文档，渲染行为不一致：
1. **margin collapsing / 末段 margin trim**：单段独立渲染时，段尾 `margin: 0 0 0.5em 0` 可能被 fwfh trim（无下一段顶住）；整页多段时，每段 margin 完整生效。
2. **文档级 baseline 对齐**：fwfh 在多 `<p>` 文档里有跨段基线计算，单段没有。
3. **fwfh 内部状态机**：整页文档触发 `BuildTree` 完整构建，单段走简化路径，line-height/font-metrics 解析不同。

这些是 fwfh 黑盒行为，**无法通过调单段公式消除**——必须让测量和渲染用完全相同的输入上下文。

## Goals

- **G1**：EPUB 纯文字章节底部不再溢出（用户截图场景根治）
- **G2**：含图片/表格/列表章节底部不再溢出
- **G3**：不显著降低当前填满率（不能为防溢出而让每页只剩一半内容）
- **G4**：翻页/进章节延迟可接受（< 500ms 增加）
- **G5**：写一个能稳定复现"用户场景 drift"的 failing test，修复后转绿

## Non-Goals

- 不重写整个分页架构（不换 CSS column、不换 fwfh 原生分页）
- 不改 paginator 的分页算法（PageBreak 结构、plain-text 坐标系不变）
- 不动 PdfRenderer（PDF 已锁死单页，无分页问题）
- 不改 ReaderProgressBar 高度（32px 底栏让出，沿用 M2.11 设计）

## Architecture Decisions

### 最终决策（2026-07-07）：本轮不修，归档调查，下一轮换库

方案 A 和 B 实测都不可行（详见下文）。fwfh 0.15.3 不是为分页设计的库，强行分页会遇各种边界问题。本轮回滚所有代码改动到稳定状态，spec/plan 作为调查归档保留。下一轮换 fwfh 0.16+ 或其他 EPUB 渲染库（如 epub_view、vocsy_epub_viewer）重做分页。

### A1（**否决**，2026-07-07 实测不可行）：重写 RenderedHtmlMeasurer 为「整页一次测量 + 迭代收敛」

**原方案**：抛弃"每段独立测量后累加"，改为每页 HTML 整体一次喂 HtmlWidget 渲染测高，对比 slot，超出则把末段推到下页，迭代收敛。

**实测结果（4 轮实现全部失败）**：
1. Column 堆叠 + GlobalKey 遍历 → fwfh 在 Column 无限高约束下 maxH 振荡（2587→4269→2587）
2. Stack 替代 Column + GlobalKey → 同样振荡
3. Stack + 回调式测量（_MeasuredPage 自报高度）→ TypeError（growable list length 扩展填 null）
4. 修完 TypeError → 振荡回归（maxH 704→1289→1874→3556 单调发散）

**根因**：fwfh 0.15.3 在"被反复重建测量"的场景下，widget 树状态不可预测。读 fwfh 源码确认：
- `buildAsync`（默认 html > 10000 字符时异步）+ `enableCaching`（缓存 widget 树）
- 强制 `buildAsync: false + enableCaching: false` **仍振荡**
- fwfh **没有官方测高 API**，`RenderMode`/`customStylesBuilder` 都是渲染控制
- 振荡本质：迭代中 `_MeasuredPage` 的 html 变化，但 fwfh 内部 BuildTree/RenderObject 状态在 widget 重建时残留旧值，测到陈旧或错误高度

**结论**：方案 A 与 fwfh 0.15.3 不兼容。需要换 fwfh 版本或换库才能走通，超出本轮范围。

### A2（**否决**，2026-07-07 实测不可行）：渲染层一次性重分页

**实测结果**：完整实现 `_PageVerticalAligner.onOverflow` 回调 + `_handleRenderOverflow` 方法。测试显示 `_handleRenderOverflow` **根本没触发**，10 页全部仍溢出 476-508px。

**未确认的失败原因**（调试需 1-2 小时，本轮已超时）：
- `KeyedSubtree` 的 RenderObject 可能不是 HtmlWidget 内容 RenderBox
- PageView lazy build 导致非当前页的 `_PageVerticalAligner` 根本没 layout
- post-frame callback 时序可能错过

**结论**：即使修好触发问题，方案 B 仍是"一次性调整"，无法根治 drift（只减少溢出量）。投入产出比低。

### A3（否决）：×1.3 安全系数

**否决原因**：drift 不是固定比例（单段 81 vs 整页 128 是 +58%，但列表/表格/图片 drift 不同）。固定系数要么过度保守（每页剩 30% 空白）要么仍漏。

### A4（否决）：换 CSS column-based 分页架构

**否决原因**：工作量过大（数周），fwfh 对 CSS column 支持不完整。本轮目标是不换架构根治。

## Risks

- **R1（迭代不收敛）**：极端章节（一段就超 slot）可能让循环死循环。**缓解**：设最大迭代轮数（如 5），达上限后用当前 breaks 兜底（接受单段超 slot，让 OverflowBox 吸收，至少不崩）。
- **R2（性能回归）**：每页一次 fwfh layout × 多轮迭代，可能让进章节明显变慢。**缓解**：缓存指纹不变则不重测（沿用 fix16 的 `_MeasurementKey`）；监控首帧延迟，若 > 500ms 加 loading 占位。
- **R3（图片异步解码仍未覆盖）**：整页测量如果在图片解码前完成，仍会漏图片高度。**缓解**：measurer 对含 `<img>` 的页等待额外帧（或用 ImageProvider.preferImmediateDecode）。本轮先治纯文字（用户场景），图片场景留 R3 在 acceptance test 观察。
- **R4（边角段落切分）**：把段从一页移到另一页，可能切在句中。**缓解**：PageBreak 本就是 plain-text offset，HtmlSlicer 已支持任意 offset 切片，切句中不丢字（只是断行位置变）。

## 防御性三件套（defense-in-depth，根因之外加固）

1. **测量层**（本 spec A1）：整页一次测量，drift 归零
2. **分页层**：paginator 的 `safetyMargin` 保留（0.3 行），作为 fwfh 跨次 layout 微漂移兜底
3. **渲染层**：`_PageVerticalAligner` 的 `OverflowBox(maxHeight: infinity)` 保留，作为最后兜底（即使前两层都漏，也不抛 RenderFlex assertion，而是溢出可见而非崩溃）
