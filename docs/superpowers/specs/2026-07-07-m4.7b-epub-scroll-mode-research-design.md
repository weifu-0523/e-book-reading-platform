> **文档性质**：M4.7 调研 spec 的补充篇章。聚焦"单页滚动浏览模式"作为第二套阅读方案。

## 1. Context（为什么单独调研滚动模式）

### 1.1 用户的洞察

用户原话：
> *"同时继续调研第二套阅读方案，及单页的滚动浏览模式，以后用户可以选择双页的翻页阅读模式或者滚动单页浏览模式，这个 Neat Reader 也实现了体验感很好。这个模式在后期 AI 功能上线后使用率很高，毕竟左右都有抽屉，展开后中间单页滚动阅读体验会更好点，双页翻页模式适合纯阅读不需要 AI 辅助的。"*

用户已经精准识别了两件事：
1. **场景分层**：纯阅读 → 双页翻页；AI 辅助阅读（左右抽屉展开）→ 单页滚动
2. **行业先例**：Neat Reader 双模式都做得好，可借鉴

### 1.2 关键技术洞察（本调研的核心发现）

M4.6-fix20 锁定的 fwfh 死结是：
> *"widget height can only be known after render, which is orthogonal to Flutter's layout system"*

但这个死结**只在分页模式下存在**——分页需要事前知道每页高度才能切分。

**滚动模式完全不需要事前测高**：
- 内容放进 `SingleChildScrollView` → Flutter 的 viewport 自动按需渲染可见部分
- 滚到哪渲染到哪，不需要预计算总高度
- fwfh 的 `RenderMode.column`（默认）在无限高度约束下会一次性渲染全部内容（chapter 级别，几十 KB HTML），性能完全可接受

**结论**：fwfh 路线在分页模式已死，但在滚动模式下完全可行。这意味着——**我们可以不做引擎切换，先恢复并打磨已有的滚动模式，作为"第二套方案"立即上线**。

## 3. 业界滚动模式技术调研

### 3.1 EPUB 3 规范层（[W3C EPUB Reading Systems 3.3](https://w3c.github.io/epub-specs/epub33/rs)）

EPUB 3 规范明确把 `rendition:flow` 定义为四种值：

| 值 | 行为 |
|---|---|
| `paginated` | 阅读系统应对溢出内容做动态分页 |
| **`scrolled-continuous`** | **可滚动 + 章节间连续滚动（一镜到底）** |
| `scrolled-doc` | 可滚动，但每个 spine item 独立滚动（章末停一下） |
| `auto` | 阅读系统自选 |

**规范背书**：滚动模式不是"次等公民"，是 EPUB 3 一等公民的 flow 模式。W3C 明确写了 `scrolled-continuous` 应"present the EPUB publication as one continuous scroll from spine item to spine item"。

### 3.2 epub.js 的滚动实现

epub.js 原生支持三种 flow：
```js
book.renderTo("area", { flow: "paginated" })       // 分页（CSS columns）
book.renderTo("area", { flow: "scrolled" })        // 滚动（连续）
book.renderTo("area", { flow: "scrolled-doc" })    // 滚动（按章）
```

机制：scrolled 模式不用 CSS columns，改用普通文档流 + `overflow-y: auto`，浏览器原生滚动。**和分页模式是同一套渲染引擎的两种 flow 配置**，切换零成本。

### 3.3 Readium 的滚动实现

[Readium CSS 注入与分页文档](https://readium.org/css/docs/CSS03-injection_and_pagination.html) 明确：

> *"if you don't want to use this [paged] model and implement yours, you can set `--RS__disablePagination: readium-noVerticalPagination-on` on the `:root`"*

Readium 把分页当成"默认但可关闭"的特性，关闭后就是滚动模式。两种模式共用同一套 CSS 注入、字体、主题、高亮。

[Readium Kotlin Navigator 偏好](https://readium.org/kotlin-toolkit/2.4.0/guides/navigator-preferences) 提供 `scroll: bool` 偏好开关，runtime 切换。

### 3.4 Neat Reader 双模式

Neat Reader 在 [Google Play 描述](https://play.google.com/store/apps/details?id=com.gzhi.neatreader.r2.main) 中明确：
> *"Choose Page or Scroll mode."*

用户评论佐证（5 星）：
> *"SCROLLING & NO ADS. I don't know why ereaders have such a hard time adding that feature to their apps."*

底层是 Readium R2（见 M4.7 spec 第 4 节），所以实现就是 Readium Navigator 的 `scroll` 偏好开关。

### 3.5 Apple Books 的滚动模式

[Apple 官方 iPad 文档](https://support.apple.com/guide/ipad/read-books-ipadc8494b6b/ipados)：
> *"Turn on vertical scrolling or change the page turn style: Tap the Page Turn button, then tap Curl, Fast Fade, or Scroll."*

Apple Books 提供 4 种翻页方式：**Curl（仿真翻页）/ Fast Fade（淡入）/ Scroll（滚动）/ Slide（滑动）**。滚动模式是其中之一，用户可即时切换。

[iOS 16 升级](https://tidbits.com/2022/10/03/apples-books-ios-16) 文档提到：
> *"In scrolling mode, the position slider on the right displays your current progress, and you can drag it to navigate within the book quickly."*

**关键 UX 细节**：滚动模式下右侧显示进度滑块（paged 模式没有，因为页码本身就是进度）。

### 3.6 微信读书

微信读书同样支持滚动/翻页切换，是国内主流 EPUB 阅读器（[weread.qq.com](https://weread.qq.com)）。其滚动模式的特点：
- 滚动时右上角浮出进度条
- 章末自动加载下一章（scrolled-continuous）
- 选中文本即弹 AI 工具栏（翻译/笔记/查询）—— **这正是用户提到的"AI 友好"场景**

### 3.7 业界共识

| 应用 | 滚动模式 | 切换入口 | AI/选区友好 |
|---|---|---|---|
| Neat Reader | ✅ | 设置页 | ✅ |
| Apple Books | ✅（4 种翻页之一）| 主题设置 | ✅ |
| 微信读书 | ✅ | 设置页 | ✅✅（核心卖点）|
| Readium Test App | ✅ | preferences | ✅ |
| Calibre Viewer | ✅（"Flow mode"）| 工具栏 | ✅ |
| Foliate | ✅ | 菜单 | ✅ |

**所有主流 EPUB 阅读器都同时支持双模式**。这是行业标配，不是可选功能。

## 4. fwfh 在滚动模式下的可用性分析

这是本调研最关键的判断点。

### 4.1 fwfh 在分页模式下的死结（M4.6-fix20 已证）

```
measurer 单段独立渲染 81px ≠ 整页实际 128px
drift = -47px（58% undercount）→ 末段被吃掉
根因：widget height can only be known after render
```

### 4.2 fwfh 在滚动模式下的表现

滚动模式的核心代码（假想）：
```dart
SingleChildScrollView(
  controller: _scrollController,
  child: Padding(
    padding: EdgeInsets.all(margin),
    child: HtmlWidget(html, textStyle: style),  // RenderMode.column 默认
  ),
)
```

关键点：
1. **`SingleChildScrollView` 给 child 的是无限高度约束**（[Flutter 文档](https://api.flutter.dev/flutter/widgets/SingleChildScrollView-class.html)："the viewport provides no maximum height constraint"）
2. **fwfh 的 `RenderMode.column`（默认）在无限高度下会一次性渲染全部内容**——这正是滚动模式想要的
3. **不需要事前测高**——Flutter 的 Sliver 系统自动按视口可见部分构建 RenderObject，滚下去时再扩展
4. **末段永远不会被"吃掉"**——因为没有"页"的概念，所有内容都在一个长卷上

**结论**：**fwfh 在滚动模式下完全可用，不存在 drift 问题**。M4.6-fix20 的死结只在分页模式下存在。

### 4.3 滚动模式的代价

- **内存**：整章 HTML 一次性渲染（几十 KB ~ 几百 KB），比 paged 模式的单页渲染略重，但现代设备可接受
- **进度计算**：用 `_scrollController.offset / maxScrollExtent` 算百分比，比 paged 模式的 `(page+1)/total` 精度低
- **Locator 映射**：charOffset ↔ pixelOffset 互转需要 TextPainter 辅助（每段量一次高度，但这是事后量，不是事前）

### 5.2 `_buildScroll` 的实际实现（`epubx_renderer.dart:1040`）

```dart
Widget _buildScroll(TextStyle style, Color fg, String html, double margin) {
  return LayoutBuilder(
    builder: (context, constraints) {
      final maxH = constraints.maxHeight.isFinite
          ? constraints.maxHeight * 0.7
          : 600.0 * 0.7;
      return SingleChildScrollView(
        controller: _scrollController,
        child: Padding(
          padding: EdgeInsets.all(margin),
          child: HtmlWidget(
            html,
            textStyle: style.copyWith(color: fg),
            customStylesBuilder: (element) => _elementStyles(element, maxH),
          ),
        ),
      );
    },
  );
}
```

**这就是 Neat Reader 滚动模式的等价实现**——`SingleChildScrollView + HtmlWidget`，没有分页逻辑，所以没有 drift。

### 5.3 缺失环节：UI 层没有切换入口

通过 grep 调查 `app/lib/` 发现：
- `setPaginationMode` 在 app 层 **零调用**
- 没有"翻页/滚动"切换按钮
- 没有设置项暴露给用户
- `reader_body.dart:226, 415, 587, 594, 740` 都只是**读** `paginationMode == PaginationMode.paged` 来做条件分支（如双页模式只在 paged 下生效），从来不**写**

**这意味着**：滚动模式的整个底层链路（renderer + 章末检测 + tap zone + Locator 重定位）都已经写好并通过测试（M3.4 时代的产物），但**被冰封了**——用户永远停在 paged 模式，根本不知道有滚动模式。

### 5.4 这个发现的战略价值

**极高**。这意味着：

1. **滚动模式可以立即（1-2 天工作量）上线**——只需要在 UI 层加一个切换按钮 + 持久化用户选择
2. **绕过 M4.7 的引擎切换决策**——如果滚动模式上线后用户主要用它（特别是 AI 场景），分页模式的 fwfh 死结就不再是阻塞点（用户可以切到滚动模式规避）
3. **M4.8 引擎切换的优先级可以降低**——滚动模式是"立刻能用"的方案，引擎切换是"长期方案"，两者并行不冲突

## 6. 双模式架构设计（参考 Neat Reader + Apple Books）

### 6.1 模式定义

```dart
enum ReadMode {
  paged,    // 翻页模式（双页或单页 PageView，左右翻页）
  scroll,   // 滚动模式（单页 SingleChildScrollView，上下滚动）
}
```

> 注：复用现有 `PaginationMode { paged, scroll }`，不改名（避免破坏现有 16 处引用）。

### 6.2 模式切换 UX（参考 Neat Reader + Apple Books）

**入口位置**：阅读区顶部工具栏（或设置面板）

**Apple Books 范式**：主题设置面板里有"翻页方式"四选一（Curl/Fast Fade/Scroll/Slide）
**Neat Reader 范式**：设置面板里"Page or Scroll mode"二选一

**智阅建议**：在现有字体/主题设置面板里加一个**"阅读模式"二选一**：
- 翻页模式（默认）
- 滚动模式

切换后立即生效，持久化到 SharedPreferences（与字号/主题同级别）。

### 6.3 模式适配规则

| 维度 | paged 模式 | scroll 模式 |
|---|---|---|
| 双页模式 | 可选（宽屏自动 / 手动 toggle）| **禁用**（滚动模式天然单列）|
| 章末提示 | 翻到最后一页触发 | 滚到 64px 内触发（已实现）|
| Tap zone | 左右翻页 | **上下换章**（已实现 `epubx_renderer.dart:260, 292`）|
| 进度条 | `(page+1)/total` 精确 | `offset/maxScrollExtent` 百分比 |
| 选区/AI | 选区跨页麻烦 | **选区天然友好**（单镜到底）|
| 左右抽屉 | 抽屉展开挤压双页 | **抽屉展开不影响**（单列自适应）|

### 6.4 AI 场景的天然契合（用户洞察验证）

用户原话：*"左右都有抽屉，展开后中间单页滚动阅读体验会更好点"*

技术验证：
- 智阅的 ReaderScaffold 已经支持左右抽屉（章节目录 / 笔记）
- paged 模式下，抽屉展开后中间阅读区被挤压 → 双页变单页，但分页逻辑还是按原宽度算的 → 翻页错位
- **scroll 模式下，抽屉展开后中间宽度变窄，SingleChildScrollView 自动 reflow，内容重新流动** → 完美

**这就是 Neat Reader / 微信读书 / Apple Books 在 AI 场景下都用滚动模式的根本原因**。

## 7. 风险与防御

### R1：滚动模式长章节性能

- **风险**：单章 100KB+ HTML 一次性渲染，低端设备可能卡顿
- **影响**：首次渲染慢、滚动掉帧
- **防御**：
  - 短期：监控 + 用户感知调查（智阅的书是金融教材类，章节普遍 < 50KB，问题不大）
  - 长期：如真有问题，改用 `ListView.builder` + 按段落懒加载（fwfh 每段独立渲染）

### R2：Locator 精度下降

- **风险**：scroll 模式用像素 offset 做 Locator，调字号/窗口大小后 offset 失效
- **影响**：重开书可能定位偏差几行
- **防御**：保存 (chapterIndex, charOffset) 而非 pixelOffset，重打开时用 TextPainter 重算 pixelOffset（M3.4 已有类似机制）

### R3：与未来引擎切换（M4.8）的关系

- **风险**：如果 M4.8 切到 WebView + epub.js，scroll 模式实现要重写
- **影响**：现在的 scroll 模式工作可能"白做"
- **防御**：**不会白做**。因为：
  - M4.7 已确认 epub.js / Readium 都原生支持 scroll flow（`flow: "scrolled"`）
  - 无论底层是 fwfh 还是 WebView，UI 层的"翻页/滚动"切换、SharedPreferences 持久化、抽屉适配逻辑都是通用的
  - 现在做 scroll 模式 = 立即解决用户痛点 + 为 M4.8 铺好 UI 路径

### R4：双页模式与滚动模式的状态切换

- **风险**：用户在 paged+双页 模式下切换到 scroll，需要优雅关闭双页
- **影响**：状态不一致可能崩溃
- **防御**：现有 `reader_body.dart:415-426` 已经处理（paged 模式才允许双页），切换 paginationMode 时自动关双页即可

## 8. 决策记录

### AD1：立即实施滚动模式（M4.7b 快速跟进）

**决策**：在 M4.8 引擎切换之前，先用 1-2 天上线滚动模式作为"第二套方案"。

**理由**：
1. **底层 95% 已实现**——只缺 UI 切换入口（grep 证据见第 5 节）
2. **绕过分页死结**——scroll 模式不需要事前测高，fwfh 完全可用
3. **立即解决用户痛点**——底部溢出问题在 scroll 模式下不存在
4. **AI 场景刚需**——用户已识别，业界共识
5. **不阻碍 M4.8**——UI 层工作可复用，底层切换时只需改 renderer 实现

### AD2：滚动模式不替代分页模式，而是并存

**决策**：保留 paged 模式为默认，scroll 模式作为可选。

**理由**：
- 用户原话已明确分层：纯阅读用 paged，AI 辅助用 scroll
- 业界（Neat Reader / Apple Books / 微信读书）都是双模式并存
- 不强迫用户迁移

### AD3：M4.8 引擎切换降级为"长期优化"

**决策**：M4.7 推荐的 A1（WebView + epub.js）从"首选"降为"长期方案"，滚动模式上线后重新评估优先级。

**理由**：
- 滚动模式上线后，用户痛点（底部溢出）已解
- 分页模式的 drift 问题变成"次要场景的小瑕疵"，不再是阻塞点
- 可以从容做 M4.8，不必赶时间
- 如果用户主要用 scroll 模式，甚至可以重新评估"是否真的需要切引擎"

## 10. 总结：两套方案的定位

| 维度 | M4.7b 滚动模式（短期） | M4.8 引擎切换（长期） |
|---|---|---|
| **目标** | 立即解决底部溢出 + AI 场景刚需 | 长期分页精度 + 富 HTML 支持 |
| **工作量** | 1-2 天（UI 接线）| 1-2 周（引擎切换 + 迁移）|
| **风险** | 低（底层已实现）| 中（桌面 WebView2 待验证）|
| **见效** | 立即 | 长期 |
| **关系** | 不阻碍 M4.8 | 不影响 M4.7b |

**建议执行顺序**：**先 M4.7b（滚动模式上线），再评估 M4.8 是否还需要做**。
