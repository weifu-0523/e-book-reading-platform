# M4.6-fix4 — 三个稳定性/排版问题修复（spec）

> 日期：2026-07-05
> 上一轮：M4.6-fix3（commit 54221f9）—— MD scroll 修复 + PDF controller nullable
> 本轮：用户测试最新 exe 后报告的三个问题

## Context（为什么做）

用户在测试 M4.6-fix3（HEAD=54221f9）后报告：

1. **exe "关掉后不能打开"**：第一次能开，关掉窗口后再点图标"闪一下就没了"
2. **PDF "翻十几页后不停加载"**：开书正常，往下翻 10+ 页后阅读区一直 loading，回退到之前正常的页也是 loading
3. **MD 阅读完全乱了**：1) 未分双页 2) 内容超出页面很多 3) 第二章标题"直接变图片"

这是 M4.6 收官前最后的稳定性冲刺。三个问题都是阻塞用户阅读的核心 bug。

## Phase 1 根因分析

### 问题 1：exe 二次启动闪退（单实例锁 + 进程残留）

**证据**：
- 用户报告"关掉后"打不开；执行 `tasklist | grep zhiyue` 显示 `zhiyue.exe PID 2932 Console 656,052 K` —— **进程未退出**
- `app/windows/runner/main.cpp:82-99`：named mutex `Local\\ZhiYueApp` 实现单实例
  - 第一实例：`CreateMutexW` 成功，`GetLastError() != ERROR_ALREADY_EXISTS` → `is_first_instance = true`
  - 第二实例：`GetLastError() == ERROR_ALREADY_EXISTS` → `is_first_instance = false`
  - 当 `argv_utf8` 为空（桌面图标双击启动无参数）→ **直接 `return EXIT_SUCCESS`**（line 98）→ 退出
- 用户看到"图标闪一下就没了" = 第二实例瞬间退出

**根因**：第一实例的"关掉窗口"并未让进程退出。Flutter Windows app 关闭窗口时，message loop `while (::GetMessage(&msg, nullptr, 0, 0))` 应当收到 WM_QUIT 退出。但本应用持有以下可能阻塞退出的资源：
- pdfrx 的 PdfDocument（native PDFium 句柄）
- window_manager 的 native window reference
- Riverpod ProviderContainer 未 dispose（持有数据库 isolate 引用）

只要 message loop 卡住任一消息处理，进程就残留。mutex 仍在内核对象表里，第二实例永远 ALREADY_EXISTS。

**最关键问题**：即使我们修了"进程残留"，单实例逻辑本身对**桌面图标双击启动**这种合法的二次启动场景也是错的——用户的合理预期是"老实例窗口前置"，而不是"什么都没有"。当前实现仅在 argv 非空时转发，argv 空时直接退出，体验糟糕。

### 问题 2：PDF 翻 10+ 页后无限加载

**证据**：
- pdfrx 2.4.4 `pdf_viewer.dart:580-584`：`_document == null` 时显示 `loadingBannerBuilder`（默认就是 CircularProgressIndicator）
- `pdf_renderer.dart:280-329`：`build()` 在 `_scannedFuture ??= ...` 后包 `FutureBuilder<bool>`，每次 `setState`/rebuild 都重建
- `pdf_renderer.dart:287`：`if (dualPageMode && !showBanner)` 切换分支时，左侧/右侧 PdfViewer 用不同 sourceName 但**共享同一个 PdfDocument**（`_doc`）
- `pdf_viewer.dart:1741` `cache.pageImages[page.pageNumber]?.dispose();` —— pdfrx 自带 pageImage 缓存，**没有 maxPinPages 上限**（已确认 2.4.4 `PdfViewerParams` 无此字段，默认 `limitRenderingCache: true` 是 PDFium 层 flag，不是 Dart 层 cache 上限）

**根因（最可能）**：
1. 单页模式下 PdfViewer 是单一 widget，pdfrx 自管页缓存，理论稳定。但本应用在 reader_body 的 LayoutBuilder 中**每次 rebuild 都重新赋值 `e.dualPageMode = isWide && !e.rendererRef.isScanned`**（line 406），这是 setter，看似幂等（line 65 `if (_dualPageMode == value) return`），但 `isScanned` 是 `_scannedCache ?? false`，scanned 判定完成后从 false → true 会触发一次 dualPageMode false→false（无副作用）→ 但**只要未来某帧 isWide 切换（窗口大小变化、滚动条出现），就会重新 setPage → _mainController.goToPage → pdfrx _invalidate → rebuild**。
2. 更深层：`setPage` 中 `_goToMainPage` 调用 `c.goToPage`，pdfrx 内部触发 `_invalidate()` → 整个 PdfViewer State rebuild → FutureBuilder rebuild → Column rebuild → **PdfViewer widget 本身因 key 不变而 State 复用，但 widget tree 父级 rebuild 可能触发 PdfViewerParams 重新构造**。PdfViewerParams 是 const 构造但本应用**每次 build 都 new 一个 `PdfViewerParams(...)` 实例**（line 304-322），按 pdfrx `doChangesRequireReload`（line 717）某些字段变化会触发 `_PdfViewerState.didUpdateWidget` → reload path。
3. pdfrx 在频繁 reload 下，`_loadDelayed` 重新触发 `loadPagesProgressively`，旧 page render cancel 但 PDFium native bitmap 已分配，反复累积 → 内存压力 → 后续 render 阻塞 → loading banner 一直显示。

**结论**：本应用对 PdfViewer 的 widget 边界处理过于脆弱——每次 build 重建 PdfViewerParams + FutureBuilder 包装 + Column 包装，导致 pdfrx 状态机不稳定。

### 问题 3：MD 阅读完全乱

**3a 排版乱（内容超出页面）**：

证据：`markdown_book_loader.dart:117-166` 的 `_preserveLineBreaks`：
```dart
// 给 body 的每行尾部补两空格，强制 hard break。
lines[i] = '$trimmedRight  ';  // line 163
```

这违反 CommonMark 语义。CommonMark spec：「段落内连续行在渲染时合并为同一段，行尾两个空格才视为强制换行」。原始 MD 文档的"一行一段"或"一行一句"只是源码可读性约定，**渲染时本就该合并**。

强行给每行加两空格 = 段内每个换行都变成 `<br>` = 段落被切成断行堆叠。fwfh 把每个 `<br>` 当硬断行渲染，**短行被垂直堆成多行**（视觉上像 "第一段在左上，第二段在右下" 是因为 fwfh 在 ScrollableRow 中错位分配，实际上是因为内容被切成过多短行导致 layout 异常）。

**修复方向**：删除 `_preserveLineBreaks` 全部逻辑。让 markdown 标准库按 CommonMark 自然合并段内行。需要保留 hard break 的情况：用户在 MD 源码里**已经**写了行尾两空格或反斜杠——这些 markdown 标准库本来就识别，无需我们干预。

**3b 第二章标题"变图片"**：

证据：用户原 MD 第二章标题可能是 `## ![image](url)` 或类似带图片语法的标题。但更可能：**markdown 标准库的 `markdownToHtml` 默认不启用图片扩展**。但 fwfh 的 HtmlWidget **默认会渲染 `<img>` 标签**，且**没有 base URL 时把 src 当网络 URL**。

需要进一步确认用户实际 MD 内容。但安全修复：禁用 fwfh 的图片渲染（MD 阅读场景不需要图片，且无网络/相对路径解析能力），或限制 `<img>` 不渲染。

**3c MD 没分双页**：

证据：`reader_body.dart:399`：
```dart
e.setDualPageMode(isWide && !e.isHtmlChaptersMode);
```
M4.6-fix2 主动把 MD/TXT 排除出双页（因为短段落结构错位）。但用户期望 MD 也双页。

**矛盾**：M4.6-fix2 排除 MD 双页是因为 paged 模式下机械分页对短段落错位；M4.6-fix3 又把 MD 改成 scroll 模式（不分页）。**scroll 模式根本不走 setDualPageMode 路径**（`_buildScroll` 是 SingleChildScrollView，没有 spread 概念）。

所以 MD 在 scroll 模式下"双页"是个伪命题——scroll 本来就是单列连续滚动。用户期望的"双页"在 scroll 模式下不存在。

**用户真实意图可能**：MD 排版正常（段落对齐、不超出边界、不分断行）即可，"未双页"是次要诉求（且 scroll 模式下确实无法双页）。优先级：**3a 排版 > 3b 图片 > 3c 双页**。

## Goals

1. **G1（问题 1）**：exe 关闭窗口后进程必须退出；二次启动应能让已有实例窗口前置（不是闪退无反应）
2. **G2（问题 2）**：PDF 翻页稳定，不会在 N 页后卡 loading
3. **G3a（问题 3a）**：MD 段落按 CommonMark 标准合并段内换行，不强制断行
4. **G3b（问题 3b）**：MD 不渲染 `<img>`（避免无意义的网络图片占位/异常显示）
5. **G3c（问题 3c）**：MD 在 scroll 模式下排版正常，文档明确 scroll 无双页概念（不做 fake 双页）

## Non-Goals

- 不改 MD 双页（scroll 模式物理上无双页；用户若坚持要双页，需先切回 paged 模式，但 paged 对 MD 段落结构不友好——这是已知 trade-off，不在本轮修）
- 不改 PDF 双页逻辑（双页代码本身没问题，问题在 widget 重建稳定性）
- 不重写 pdfrx 缓存管理（上游问题，workaround 在应用层）

## Architecture Decisions

### A1：exe 退出 = 进程退出（强制）

**决策**：在 `main.cpp` 的 message loop 退出后，**强制调用 `ExitProcess(0)`** 而非依赖 `return EXIT_SUCCESS`。这样即使 Flutter engine 有未释放资源导致 message loop 异常，进程也会被强制终止。

但更稳妥的做法是**根治"窗口关闭时进程不退出"**。Flutter Windows app 的 `SetQuitOnClose(true)`（main.cpp:111）应当让窗口关闭 → WM_QUIT → message loop 退出 → return。如果不退出，说明 GetMessage 卡住。这种情况通常源于某个 native plugin（pdfrx / window_manager）在窗口 destroy 时阻塞。

**采用方案**：
1. **A1.1**：`wWinMain` 末尾 message loop 退出后强制 `::ExitProcess(EXIT_SUCCESS)`（兜底，根治 mutex 残留）
2. **A1.2**：第二实例发现已有实例时，**总是**（即使 argv 空）尝试把已有窗口前置（`SetForegroundWindow`），而不是无操作退出。这需要给窗口标记 HWND（已有 `kZhiYueWindowProp`），新增逻辑：枚举到目标窗口后 `SetForegroundWindow` 再退出。

### A2：PDF widget tree 稳定化

**决策**：把 PdfRenderer 的 `build()` 重构为：
- **A2.1**：把 `PdfViewerParams` 提取为**实例字段**，仅在 `_typography` / `_currentPage` 变化时重建（而不是每次 widget build 都 new）。这避免父级 rebuild 时 pdfrx 触发 reload。
- **A2.2**：把 `FutureBuilder<bool>`（scanned 判定）的**结果缓存到 `_scannedCache` 后**，build 走同步分支返回 PdfViewer，**不再每次包 FutureBuilder**。`_scannedFuture` 完成后调一次 `onScannedResolved` 回调，setState 让 build 用同步路径。
- **A2.3**：`build()` 顶层包一个 `RepaintBoundary`，把 PDF 阅读区与 reader_body 父级隔离开，减少跨区 rebuild 传播。
- **A2.4**：PdfViewer 加 `key: ValueKey(_doc?.sourceName)` —— 同书 sourceName 不变 → State 复用稳定；切书 sourceName 变 → 干净重建。

### A3：MD 移除强制 hard break

**决策**：删除 `_preserveLineBreaks` 全部逻辑，`_markdownToHtml` 直接走 `md.markdownToHtml(body)`。CommonMark 标准库已正确处理：
- 段内单换行 → 合并（用户源码可读性，渲染应合并）
- 行尾两空格 / 反斜杠 → hard break（用户显式意图，保留）
- 空行 → 段落分隔
- 标题/列表/引用/代码块 → 结构正确渲染

### A4：MD 禁用图片渲染

**决策**：在 `_buildScroll` 的 `HtmlWidget` 配置中显式禁用 `<img>` 渲染。fwfh 提供 `renderMode` / 自定义 `factoryBuilder`，但最简单：在 markdown 转 HTML 时**过滤掉 `![...]()` 图片语法**，或在 HtmlWidget 的 `customStylesBuilder` 里把 `<img>` 设 `display: none`。

更稳妥：在 `_markdownToHtml` 后用 html parser 移除所有 `<img>` 标签。MD 阅读场景无网络/相对路径，图片本来也无法正确显示，移除是合理 trade-off。

## Risks

- **R1**：A2 PdfViewerParams 改成实例字段后，如果 `buildContextMenu` 闭包捕获了 `_currentPage`，可能读到 stale 值。**缓解**：`buildContextMenu` 用 `fallbackPage: _currentPage + 1` 但 context menu 触发时 pdfrx 自带 `params.a?.page.pageNumber`，fallback 仅边界场景，影响小。
- **R2**：A1.1 `ExitProcess` 强制退出可能跳过 Dart `dispose()` 路径，导致数据库未 flush。**缓解**：Flutter `AppLifecycleState.detached` 通常在窗口 destroy 前触发，drift 在 WAL 模式下写入已落盘；且当前已知"自然退出路径已挂死"，强制退出比残留 mutex 强。
- **R3**：A4 移除 MD 图片可能误删合法的 data URI 内嵌图。**缓解**：MVP 阶段 MD 用户量小，先全部移除；后续可只移除非 data: 的 img。

## Success Criteria

1. exe 双击启动 → 关闭窗口 → 再次双击能再次启动（进程不残留）
2. exe 已运行 → 再次双击图标 → 已有窗口前置（不闪退）
3. PDF 打开后翻 50+ 页不卡 loading
4. MD 文件打开后段落正常合并，不超出边界，无图片异常渲染
5. 已有的 EPUB / TXT / PDF 单页渲染不回归
6. 现有所有测试通过（包括 M4.6-fix3 的 MD scroll 集成测试）
