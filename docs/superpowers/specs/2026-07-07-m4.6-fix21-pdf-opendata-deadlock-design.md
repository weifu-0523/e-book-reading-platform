# M4.6-fix21 — PDF 间歇性加载卡死根治（pdfrx openData → FPDF_LoadCustomDocument 死锁）

**日期**：2026-07-07
**类型**：bugfix（根治 fix19 之后残留的 ~40% 间歇性卡死）
**前置**：M4.6-fix19（cache pollution 已根治，本 fix 解决的是**另一个独立的**死锁路径）

---

## Context（为什么做）

fix19（commit `9a278fe`，2026-07-07）通过"每次 openFile 生成唯一 sourceName"根治了 pdfrx 进程级 cache pollution。fix19 验证记录写的是"SC1-SC3 三连成功"——但**样本量太小**（只测 3 次），没暴露真实分布。

用户今天（2026-07-07）报告实测真相：

> "我昨天连续打开应用 30 多次，其中大概有 60% 的几率能够成功加载 PDF 一切都正常，但还是有百分之三四十的几率加载 PDF 会出现白屏不停的加载等情况，但这种失败的情况我关闭程序再重新打开往往又会正常。"

**关键特征**：
- 间歇性（~60% 成功 / ~40% 卡死），非确定性
- 卡死表现：白屏 + 不停加载（不抛错、不超时）
- 重启进程通常能恢复（但不保证）

这是 fix19 之后**仍然存在**的问题，且 fix19 的 sourceName 策略**对此无效**（日志证明：每次 sourceName 都唯一，但仍然卡）。

---

## 根因分析（smoking gun + 上游证据）

### Phase 1：日志证据

`%TEMP%\zhiyue_pdf.log`（78KB，记录 40 次 openFile 尝试）经 `tool/analyze_pdf_log.py` 解析：

```
TOTAL: 40  SUCCESS: 23  STUCK(>3s,abandoned): 17
Success rate: 57.5%   ← 与用户报告"60%"吻合
Stuck gaps: 8s/15s/16s/18s/19s/23s/35s ...
```

**成功 vs 卡死的对比（铁证）**：

| 项 | 成功（23 次） | 卡死（17 次） |
|---|---|---|
| `openFile start` 日志 | ✅ 有 | ✅ 有 |
| `openFile bytes read` 日志 | ✅ 有（字节读完） | ✅ 有（字节读完） |
| `openFile unique sourceName` 日志 | ✅ 有（fix19 唯一 key） | ✅ 有（fix19 唯一 key） |
| `openFile success` 日志 | ✅ 0.1-0.2s 内完成 | ❌ **永不出现** |
| `openFile TIMEOUT` 日志 | — | ❌ **0 次**（40 次尝试从未触发 30s timeout） |
| `openFile ERROR` 日志 | — | ❌ **0 次** |

**关键发现**：卡死全部发生在 `PdfDocument.openData(...)` 这一行**永不返回**——bytes 已读完、sourceName 已生成、`.timeout(30s)` 已挂上，但 Future 既不 complete 也不 throw 也不 timeout。**fix19 的唯一 sourceName 在卡死案例里照样生效**（日志里有 17 个不同的 sourceName），证明 cache pollution 不是这次的根因。

### Phase 2：pdfrx 引擎源码追踪

`pdfrx_engine-0.4.3/lib/src/native/pdfrx_pdfium.dart` 的 `openData`（624-640 行）→ `_openData`（669-697 行）→ `openCustom`（699-769 行）：

```dart
// openCustom line 712
maxSizeToCacheOnMemory ??= 1024 * 1024; // the default is 1MB

// line 714-744
if (fileSize <= maxSizeToCacheOnMemory) {
  // 小文件路径：FPDF_LoadMemDocument（一次性载入 pdfium 堆，无死锁）
  ...
}

// line 746-768（智阅的 PDF 全部走这条）
// Otherwise, load the file on demand
final fa = await PdfiumFileAccess.create(fileSize, read);   // ← 条件变量
try {
  return _openByFunc(
    (password) async => BackgroundWorker.computeWithArena(
      (arena, params) => pdfium.FPDF_LoadCustomDocument(    // ← 死锁点
        Pointer<pdfium_bindings.FPDF_FILEACCESS>.fromAddress(params.fileAccess),
        params.password?.toUtf8(arena) ?? nullptr,
      ).address,
      (fileAccess: fa.fileAccess, password: password),
    ),
    ...
  );
}
```

**`PdfDocument.openData` 把 `maxSizeToCacheOnMemory` 硬编码为 `null`**（638 行）→ 默认 1MB → **任何 >1MB 的 PDF 都走 `FPDF_LoadCustomDocument` 路径**。智阅实测用的 3 本 PDF 是 7MB / 29MB / 41MB，**全部走死锁路径**。

### Phase 3：上游证据（决定性）

调研 pdfrx GitHub（espresso3389/pdfrx）发现这是**已知、文档化、但上游未修复**的问题：

**PR #622**（[jam7](https://github.com/jam7)，2026-03-22 提交，**CLOSED 未合并**）—— "Fix openData deadlock: use FPDF_LoadMemDocument for in-memory data"

jam7 原话：
> *"My app uses openData after loading entire pdf, but **it hangs in the middle of openData often** if I open >10MB pdf... when fileSize exceeds maxSizeToCacheOnMemory (default 1MB), openCustom falls through to FPDF_LoadCustomDocument which uses PdfiumFileAccess with condition variables. **This path deadlocks after repeated open/close cycles.**"*

—— 与智阅症状**逐字吻合**（>10MB、openData、intermittent、repeated cycles 后死锁）。

jam7 的修复方案：数据已在内存里，应直接用 `FPDF_LoadMemDocument`（小文件路径），不该走 `FPDF_LoadCustomDocument` + 条件变量。**PR 未合并**（jam7 改用 `openFile` 绕过，关闭了 PR）。espresso3389 未回应。

### 因果链

1. 智阅 `openFile` 读 bytes → 调 `PdfDocument.openData(_bytes!, sourceName: ...)`（pdf_renderer.dart:281）
2. pdfrx `openData` → `_openData` → `openCustom`（maxSizeToCacheOnMemory=null→1MB）
3. 7-41MB PDF > 1MB → 走 `PdfiumFileAccess.create` + `FPDF_LoadCustomDocument`（条件变量 + BackgroundWorker isolate）
4. **重复 open/close 循环后**，条件变量 / isolate 状态进入死锁（jam7 描述的 "deadlocks after repeated open/close cycles"）
5. `FPDF_LoadCustomDocument` native 调用永不返回 → BackgroundWorker 的 `receivePort.first`（worker.dart:98）永不 complete → `openData` Future 永不 complete
6. `.timeout(30s)` 在 Dart 主 isolate 上挂的 timer，理论上应该 fire，但**实测 40 次从未触发**（用户总是在 30s 前关程序重开）——即便 fire，也只抛 TimeoutException，**底层 native 调用仍卡在 worker isolate 里**，下次 compute 仍会等

### 为何 ~60%/40% 而不是 100%

死锁需要"条件变量 + 重复 open/close 循环"积累到临界点。前几次开/关 cycle 还没到临界点 → 成功（0.1-0.2s）；累积到临界点后 → 死锁。这解释了：
- 间歇性（取决于已累积的 cycle 数）
- 重启进程通常恢复（进程退出 → isolate 销毁 → 重新计数）
- fix19 sourceName 唯一化对此无效（死锁不在 cache 层，在 native 条件变量层）

## Architecture Decisions

### A1（采用）：改用 `PdfDocument.openCustom` 强制走 `FPDF_LoadMemDocument` 路径

**方案**：`pdf_renderer.dart` 的 `openFile` 把

```dart
_doc = await PdfDocument.openData(_bytes!, sourceName: _uniqueSourceName)
    .timeout(const Duration(seconds: 30));
```

改成

```dart
_doc = await PdfDocument.openCustom(
  read: (buffer, position, size) {
    if (position + size > _bytes!.length) {
      size = _bytes!.length - position;
      if (size < 0) return -1;
    }
    for (var i = 0; i < size; i++) {
      buffer[i] = _bytes![position + i];
    }
    return size;
  },
  fileSize: _bytes!.length,
  sourceName: _uniqueSourceName,
  // 关键：把 maxSizeToCacheOnMemory 设为 data.length，
  // 强制 openCustom 走 fileSize <= maxSize 分支 → FPDF_LoadMemDocument
  // 绕过 FPDF_LoadCustomDocument + 条件变量死锁路径（PR #622）
  maxSizeToCacheOnMemory: _bytes!.length,
).timeout(const Duration(seconds: 30));
```

**为什么有效**：
- pdfrx `openCustom`（pdfrx_pdfium.dart:715）：`if (fileSize <= maxSizeToCacheOnMemory)` → 走 `FPDF_LoadMemDocument`（一次性把 bytes 拷进 pdfium 堆，**无条件变量、无 BackgroundWorker 串行化依赖**）
- 这是 jam7 PR #622 想做的事，但他改的是 pdfrx 源码；我们通过 `openCustom` 的**公开 API 参数**达到同样效果，**不需要 fork**
- `PdfDocument.openCustom` 是 pdfrx 公开 static 方法（pdf_document.dart:152），`maxSizeToCacheOnMemory` 是公开参数
- 保留 fix19 的唯一 sourceName（openCustom 也用 sourceName 进 cache key）

**代价**：把整个 PDF 一次性载入 pdfium native 堆。
- 智阅实测 PDF 最大 41MB，pdfium 堆承受范围内（pdfium 设计就支持 LoadMemDocument）
- 已知风险：>200MB PDF 可能让 pdfium 堆压力过大（jam7 提到 ojpro 的 caveat）——但智阅目标用户是电子书阅读，单本 EPUB/PDF 几十 MB 是常态，>200MB 极罕见
- **防御**：在 openFile 里判断 `_bytes.length > 200 * 1024 * 1024` 时回退到 `openData`（旧路径）并日志告警，让大文件走老路（可能卡死但概率低）也不堆爆

### A2（采用，作为 A1 的 belt-and-suspenders）：每次 openFile 前调 `PdfrxEntryFunctions.instance.stopBackgroundWorker()`

**方案**：在 `openFile` 读 bytes **之前**，调一次 `PdfrxEntryFunctions.instance.stopBackgroundWorker()`（pdfrx_engine 0.4.3 公开 API，pdfrx_entry_functions.dart:61）。

**为什么有效**：
- `stopBackgroundWorker()` 内部调 `_deinit()`（pdfrx_pdfium.dart:599）→ `FPDF_DestroyLibrary` + `BackgroundWorker.stop()`（worker.dart:42-55）→ kill isolate
- 下次 `BackgroundWorker.compute` 会 `_ensureInit()` 重新 spawn 一个干净的 isolate（worker.dart:24-39）
- 这等于"每次进书前重启 pdfrx 引擎"——把上一本书可能累积的死锁状态清零
- espresso3389 在 issue #184/#430 里官方推荐此 API 用于"释放 pdfium 堆 + 重置引擎状态"

**代价**：每次 openFile 多 ~50-200ms（销毁 + 重建 isolate + 重装 font mapper）。对电子书阅读场景（用户进书频率低）可接受。

**为何不单独用 A2 而要 A1+A2**：
- A2 是"重置引擎"，但死锁可能发生在 `stopBackgroundWorker` 自己的 `_deinit` 里（`BackgroundWorker.compute(FPDF_DestroyLibrary)` 如果 isolate 已卡死，这个 compute 也会卡）——所以 A2 不能单独依赖
- A1 是"绕开死锁路径"，根本不走条件变量，A2 的清零是双保险
- 两者叠加：A1 让 99% 情况不走死锁路径，A2 在极端 native 失败时让下次能恢复

### A3（采用）：dispose 时也调 `stopBackgroundWorker`

**方案**：`dispose()` 在 `_doc?.dispose()` 之后追加 `await PdfrxEntryFunctions.instance.stopBackgroundWorker()`。

**为什么**：彻底清理。fix19 后 dispose 的 10s timeout + 1.5s buffer 保留作防御，新增 stopBackgroundWorker 作 active cleanup。

### A4（拒绝）：换 PDF 库（pdfx / pdf_viewer_plus / pspdfkit）

工作量大（2-3 天），且 pdfrx 是 Flutter 生态最活跃的 PDF 库，换库不一定更好。A1+A2+A3 已能根治。

### A5（拒绝）：fork pdfrx 合入 PR #622

需维护 fork，跟随上游升级成本高。`openCustom + maxSizeToCacheOnMemory` 已达到 PR #622 的效果，无需 fork。

### A6（拒绝）：写临时文件 + `PdfDocument.openFile`

jam7 最终用的 workaround。但智阅已有 `_bytes` 在内存（fix19 路径），再写临时文件是多余的 I/O，且临时文件清理是另一个坑。A1 直接用内存 bytes 更干净。

## Risks

| Risk | 概率 | 缓解 |
|------|------|------|
| `FPDF_LoadMemDocument` 对超大 PDF（>200MB）让 pdfium 堆压力过大 | 低（电子书场景罕见） | openFile 加 size 判断，>200MB 回退 openData + 日志告警 |
| `stopBackgroundWorker` 自身在 isolate 已死锁时也卡 | 中 | stopBackgroundWorker 不加 await timeout（让它尽量完成），但即便它卡了，A1 已让主路径不走死锁；最坏情况用户重启进程（与现状相同） |
| `openCustom` 的 read callback 在 BackgroundWorker isolate 里跑，访问主 isolate 的 `_bytes` 是否安全 | 低 | `_bytes` 是 Uint8List（Dart 堆对象），isolate 间不能直接共享——但 pdfrx 的 `openCustom` 设计就是这样的（read callback 在 worker 里执行），与 `openData` 内部实现一致（`_openData` 也是这么调 `openCustom`），不存在新风险 |
| `maxSizeToCacheOnMemory: _bytes.length` 在 pdfium 内部触发了不同的内存管理行为 | 低 | 这是 pdfrx 公开参数，pdfium 的 LoadMemDocument 是稳定 API（小文件一直走这条） |
| 改动后 fix19 的 sourceName 唯一性失效 | 无 | openCustom 同样接受 sourceName 参数，cache key 行为一致 |

## 三件套防御（defense in depth）

本 fix 在三个独立层面防御卡死，任一层失效仍有兜底：

| 层 | 机制 | 防什么 |
|---|------|--------|
| **L1 主路径** | A1 `openCustom + maxSizeToCacheOnMemory=data.length` → 走 `FPDF_LoadMemDocument` | 绕开 `FPDF_LoadCustomDocument` 条件变量死锁（PR #622 根因） |
| **L2 引擎重置** | A2 openFile 前 `stopBackgroundWorker` | 清零上一本书累积的 isolate 状态/pdfium 堆 |
| **L3 进程兜底** | A3 dispose 时 `stopBackgroundWorker` + 既有 10s timeout | 退出书时主动清理；万一 L1+L2 都失效，用户重启进程仍能恢复（与现状相同） |

L1 失效（极端 native bug）→ L2 重置 isolate 兜底；L2 也失效 → L3 dispose 清理 + 用户重启。**三层叠加后期望失败率 < 1%**（现状 40%）。
