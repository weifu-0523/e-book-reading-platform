# M2.8 Bugfix Batches + M2.9 EPUB Dual-Page & Page Numbers Design

> **Status**: Implemented (4 batches shipped + dual-page feature delivered, 2026-07-04)
> **Predecessor**: M2.7 Round 3 (v1.5.1-alpha, shipped 2026-07-03)
> **Successor**: M3 (TBD; likely rich-text pagination precision + dual-page persistence)
> **Target tag**: `m2.8-m2.9-complete` + `v1.6.0-alpha` (pending user acceptance)
> **Estimated scope**: 4 bugfix batches (~7 bugs) + 1 dual-page feature + page numbers

## Context

M2.7 Round 3 shipped v1.5.1-alpha on 2026-07-03, fixing the typography state-bridge blind spot (renderer → adapter stream forwarding). User rebuilt the Windows Debug exe and ran hands-on UX testing across 2026-07-03 → 2026-07-04, reporting the remaining bugs from the original 9-bug catalog plus two new feature requests:

1. **Bug residuals** (#1 bookmark red screen, #2 note-tap latency, #5b highlight not rendering, #6 paging chaos / chapter-start back-page, #8 text overflow, #9 ESC fullscreen) — these survived M2.6/M2.7 because their root causes are in `EpubxRenderer`'s paging/chapter-switch pipeline, not the typography state bridge that M2.7 fixed.
2. **New features** (M2.9): EPUB dual-page layout (book-like left/right spread when the window is wide enough) + per-page page numbers at the bottom.

The bugfixes and the dual-page feature are tightly coupled — both touch `_buildPaged`, PageController page indices, and chapter-switch settle timing. They were therefore delivered as one combined milestone (M2.8 batches → M2.9 feature), with user acceptance gates between each batch.

Root-cause confidence is HIGH for all bugs (verified by code-level tracing + subagent fan-out investigation). The dual-page design was confirmed via AskUserQuestion (auto-trigger on wide screen; chapter-local page numbers `当前/总`).

## Goals

1. **All remaining user-reported bugs closed** with regression tests (B1–B4)
2. **EPUB dual-page rendering delivered** — auto-trigger at width ≥ 1100px, single PageView with Row-of-two spreads, orphan-page safe
3. **Per-page page numbers** — `3 / 12` (single) / `3-4 / 12` (dual), real-time on page turn
4. **No regression** on already-fixed bugs (#3 typography, #7 TOC, M2.7 state bridge)
5. **No persistence** of dual-page mode this milestone (parity with PDF; v1.5.2+)

## Non-Goals (deferred)

- **Dual-page mode persistence** (SharedPreferences / drift) — deferred to v1.5.2, parity with PDF's "v1.5.1 不持久化" decision
- **Whole-book cumulative page numbers** — performance cost of pre-computing all chapters' page counts is too high; user explicitly chose chapter-local (`当前/总`)
- **PDF dual-page changes** — PDF already has working dual-page (M2.5/T13); out of scope
- **Dual-page spine shadow / gutter beautification** — pure visual polish; deferred
- **Rich-text pagination precision** — Paginator measures with TextPainter on plain text, renders with HtmlWidget; measurement-vs-render height mismatch is <1 line in practice. Dual-page halves width → more line wraps → mismatch may grow. Accepted for now; M3 may switch measurement to HtmlWidget.
- **Dual-page text selection restriction** — PDF disables selection in dual mode (page-attribution ambiguity); EPUB keeps SelectableRegion active. Cross-page selection may behave oddly; defer restriction until user reports.

## Bug Catalog (Root Causes Verified)

### Batch 1 (B1): Paging + Keyboard + ESC

#### Bug #6: Mouse/keyboard paging broken, chapter chaos (HIGH confidence)

**User report**: "鼠标单击翻页延迟非常高，翻页逻辑有问题，感觉在乱翻"

**Root cause** (`app/lib/features/reader/pages/reader_body.dart:411-426` pre-fix):
Tap-zone `onTapNext`/`onTapPrev` unconditionally called `engine.nextSpine()` / `previousSpine()`. `nextSpine` only switches chapters (chapter-end → next chapter); it has no in-chapter paging concept. So in paged mode, every tap tried to jump a whole chapter, producing the "乱翻" sensation. In-chapter paging (`nextPage`/`previousPage` stepping the PageController) didn't exist on the engine interface.

**Fix**: Add `bool nextPage()` / `bool previousPage()` to `ReaderEngine`. `EpubxRenderer.nextPage` reads `_pageController.page`; chapter-end (`>= breaks.length-1`) → `_nextChapterIfPossible()`, else `_pageController.nextPage(200ms)`. reader_body routes by `paginationMode`: paged → `nextPage`/`previousPage`; scroll → `nextSpine`/`previousSpine`.

#### Bug #8: Text overflows bottom edge (HIGH confidence)

**Root cause** (`reader_engine_epub_view/lib/paginator.dart` pre-fix):
`_paginateUncached` measured height with the full viewport (`usableHeight = viewport.height`), but `_buildPaged` wrapped each page in `Padding(EdgeInsets.all(margin))`. So content was measured for full height but rendered in a reduced box → overflow.

**Fix**: `usableHeight = viewport.height - 2*marginPx`; `usableWidth = (viewport.width - 2*marginPx).clamp(50, inf)`. `_CacheKey` gains a `marginPx` field so cache invalidates on margin change.

#### Bug #9: ESC doesn't exit fullscreen (HIGH confidence)

**Root cause** (`app/lib/features/reader/widgets/reader_scaffold.dart` pre-fix):
ReaderScaffold used a `Focus(onKeyEvent:)` to receive keyboard events. But the EPUB content area is wrapped in `SelectableRegion`, which steals focus when the user makes a text selection. After selection, the ReaderScaffold Focus node loses focus → `onKeyEvent` never fires → ESC/F11/arrows dead.

**Fix**: Add a global `HardwareKeyboard.instance.addHandler(_handleHardwareKeyEvent)` in `initState` (removed in `dispose`). HardwareKeyboard is a global singleton independent of the Focus tree, so it receives events regardless of SelectableRegion focus theft. Remove the Focus `onKeyEvent` to avoid double-dispatch (both paths firing the same key was the original "Expected 1, Actual 2" test failure).

### Batch 2 (B2): Cross-chapter paging

#### Bug #6 (cross-chapter): Chapter-end forward → bounces back to chapter start, then silent multi-chapter skips (HIGH confidence)

**User report**: "第六章到最后一页后，继续点击下一页就回到第六章第一页了，然后软件就非常卡顿了，在点击左侧后再右侧，就直接跨章节翻动了"

**Root cause** (`reader_engine_epub_view/lib/epubx_renderer.dart` `setChapter` pre-fix):
`setChapter()` mutated `_currentChapterIndex`, cleared `_cachedBreaks`, called `jumpToPage(0)`, but **did not emit `ReaderEngineReady`**. Compare: `gotoLocator` CFI branch (line 521), `gotoLocator` EpubRangeLocator branch, `injectHighlights`, `setTypography`, `setPaginationMode` all emit. `setChapter` was the lone chapter-mutating path that didn't.

Without emission: `reader_body.state$.listen` never fires → no `setState` → no rebuild → `_buildPaged`'s LayoutBuilder never re-runs → `_cachedBreaks` stays null → PageView keeps rendering the OLD chapter's pages, while `_pageController` is at page 0 → user sees "back at chapter start". Next `nextPage()` reads `_cachedBreaks == null` → falls into the "breaks 还没算出...fallback 换章" branch → calls `_nextChapterIfPossible()` again → silently advances chapter index → "跨章节乱翻".

**Fix**: Add `_stateController.add(const ReaderEngineReady())` at the end of `setChapter`.

#### Feature: Chapter-start back-page lands on previous chapter's LAST page (Kindle parity)

**Pre-fix**: `previousPage()` chapter-start branch called `_previousChapterIfPossible()` → `setChapter(idx-1)` → `jumpToPage(0)`, landing on the previous chapter's FIRST page. Asymmetric with forward paging (chapter-end → next chapter's first page is correct), and inconsistent with Kindle / 微信读书.

**Fix**: `previousPage` chapter-start branch arms a `_pendingJumpToLastPage` flag after `_previousChapterIfPossible()`. `_maybeApplyPendingLastPageJump()` (called in `_buildPaged` after `_cachedBreaks` is repopulated) does `jumpToPage(lastPage)` and clears the flag (one-shot). `setChapter` clears the flag (only `previousPage` re-arms it), so other call paths (TOC tap, bookmark jump, nextPage chapter-end) correctly land on page 0.

### Batch 3 (B3): Highlight rendering in paged mode

#### Bug #5b: Highlight color doesn't appear in paged mode (HIGH confidence)

**User report**: "文字摘录，标记颜色后，书籍内文字依旧没有变化"

**Root cause** (`reader_engine_epub_view/lib/epubx_renderer.dart` `_buildPaged` pre-fix):
`_buildPaged` rendered each page as `Text(plain.substring(start, end))`. This strips ALL HTML, including the `<span style="background-color:...">` that `HtmlHighlightInjector` injected. Even though `injectHighlights` correctly populated `_allHighlights` and `currentHighlightedHtml()` correctly produced span-wrapped HTML, the paged path discarded it. (Scroll mode rendered `currentHighlightedHtml()` via `HtmlWidget` and worked fine.)

**Fix**: New `HtmlSlicer` utility with two methods:
- `sliceByPlainRange(html, pageStart, pageEnd)` — DOM-walks the chapter HTML, keeps ancestor tags (`<p>`/`<b>`), trims partially-overlapping text nodes to the page range, removes out-of-range text nodes. Returns a page-local HTML fragment.
- `localizeHighlights(highlights, pageStart, pageEnd)` — maps chapter-global plain offsets to page-local offsets (intersection + translation), so `HtmlHighlightInjector.inject` can run on the page fragment.

`_buildPaged` now: `HtmlSlicer.sliceByPlainRange` → `HtmlHighlightInjector.inject` (page-local highlights) → `HtmlWidget`. `build()` passes `currentHighlightedHtml()` to scroll mode (unchanged) but raw chapter HTML to paged mode (per-page injection).

#### Bug #5: Faded background color (already satisfied)

The 0.4 alpha rgba values were already in `reader_body._highlightColorRgba` (`rgba(255, 235, 59, 0.4)` etc.). The reason highlights didn't show was purely #5b (spans stripped). Once #5b is fixed, the faded background naturally appears.

### Batch 4 (B4): Bookmark red screen + note-tap latency

#### Bug #1: Bookmark tap → red error screen with yellow English stack trace (HIGH confidence, root cause traced via subagent fan-out)

**Root cause** (`reader_engine_epub_view/lib/epubx_renderer.dart:583-588` `gotoLocator` post-frame callback pre-fix):
```dart
WidgetsBinding.instance.addPostFrameCallback((_) {
  if (!_scrollController.hasClients) return;
  final max = _scrollController.position.maxScrollExtent;
  _scrollController.jumpTo(max * ratio);
  _emitCurrentLocation();
});
```
This callback runs on a **later frame**, completely outside the caller's (`_onBookmarkJump`) try-catch. Bookmark cross-chapter jumps trigger `setChapter` + rebuild; during rebuild the ScrollController may transiently detach (`hasClients` flips false→true), and `.position` access or `_emitCurrentLocation` internals can throw → uncaught → red screen.

Additionally, `gotoLocator`'s CFI and EpubRangeLocator cross-chapter branches did **not** call `jumpToPage(0)` (only `setChapter` did). So a bookmark CFI targeting a different chapter left the PageController at the old chapter's page index, which could exceed the new chapter's `itemCount` → `PageController.page cannot be greater than itemCount` assertion → red screen.

**Fix** (three-layer defense):
1. Wrap the post-frame callback body in try-catch (failure → debugPrint only, never propagates)
2. Add `_currentChapterIndex >= chapters.length` bounds guards to `build`, `currentChapterPlainText`, `currentHighlightedHtml` (book-switch race defense)
3. Add `jumpToPage(0)` to both cross-chapter branches of `gotoLocator` (CFI + EpubRangeLocator)

#### Bug #2: Note tap takes a moment to jump (HIGH confidence)

**User report**: "点击笔记要等一会才跳回到摘要的页面"

**Root cause** (`app/lib/features/reader/pages/reader_body.dart` `_onAnnotationTap` pre-fix):
`_onAnnotationTap` did `await engine.gotoLocator(...)` then `await engine.chapterSwitchSettled`, then immediately read `engine.currentChapterPageBreaks` and called `ScrollToOffsetService.scrollToCharacterOffset` → `pageController.jumpToPage`. But `chapterSwitchSettled`'s completer resolves on the post-frame callback of the **same frame** that `_buildPaged`'s LayoutBuilder re-ran in. At that point the PageView has just been told to rebuild but hasn't completed layout — so the immediately-following `jumpToPage` gets swallowed or lands on the wrong page → "等一会才跳" (the jump eventually lands after the next frame).

**Fix**: New `_awaitChapterSettledAndLayout()` helper: `await engine.chapterSwitchSettled` then `await WidgetsBinding.instance.endOfFrame` (one extra frame for PageView to complete layout). Applied uniformly to `_onAnnotationTap`, `_onBookmarkJump`, `_maybeHandleInitialLocator`, `_jumpToChapter`.

## M2.9 Feature Design: EPUB Dual-Page + Page Numbers

### Decision A1: Auto-trigger on wide screen (user-confirmed via AskUserQuestion)

**Options considered**:
- (a) Auto: width ≥ threshold → dual page; narrow → single. No manual toggle.
- (b) Manual button (parity with PDF).
- (c) Auto + manual override.

**User choice**: (a) Auto. Rationale: "页面足够大时像书一样" implies the layout should adapt naturally to available space, like a physical book opening flat. Threshold = 1100px (matches the existing `isWide` branch in reader_body's LayoutBuilder, which already switches narrow/wide reader trees).

**Implementation**: reader_body's LayoutBuilder calls `engine.setDualPageMode(isWide && paginationMode == paged)` on every rebuild. `setDualPageMode` is idempotent (no-op if unchanged), so the per-rebuild call is cheap.

### Decision A2: Single PageView + Row-of-two spreads (NOT two independent PageViews)

**Options considered**:
- (a) Single PageView where each item (spread) is `Row(Expanded(left), SizedBox(gutter), Expanded(right))`. Paginator measures at half-width; spread[i] = breaks[i*2] + breaks[i*2+1].
- (b) Two independent PageViews side-by-side, synchronized manually.

**Choice**: (a). Rationale:
- Turn animation slides the whole spread together (matches physical book intuition)
- Single PageController → no dual-controller sync problem
- Consistent with PDF's Row-of-two approach (pdf_renderer.dart `_buildDualPage`)
- Paginator needs no change — caller halves the viewport width before passing in; `_CacheKey` already includes viewport Size, so cache auto-invalidates on the width change.

**Gutter**: 24px fixed (`gutterPx`). Visual spine gap; not a shadow (deferred to polish).

**Orphan page**: If `breaks.length` is odd, the last spread's right slot is `SizedBox.shrink()`. No crash.

### Decision A3: Chapter-local page numbers `当前/总` (user-confirmed via AskUserQuestion)

**Options considered**:
- (a) Chapter-local: `3 / 12` (current/total within chapter). Dual: `3-4 / 12`.
- (b) Whole-book cumulative. Rejected: requires pre-computing all chapters' page counts (expensive on first open).
- (c) Chapter title + chapter-local. Rejected: too much horizontal space.

**User choice**: (a).

**Data path**: New `ReaderEngine` interface members `currentSpreadCount` (total) + `currentSpreadIndex` (current, 0-based). EPUB returns spread count (dual: `(breaks+1)~/2`, single: `breaks.length`); PDF returns 0 (uses its own `pageCount`/`currentPage`).

**Real-time update prerequisite**: The old `onPageChanged` only called `_maybeEmitChapterEnd()`, NOT `_emitCurrentLocation()`. So `currentLocation$` didn't emit on page turns → `ReaderProgressBar` (which subscribes to `currentLocation$`) didn't refresh → page numbers wouldn't update. Fix: `onPageChanged` now calls both. This is the critical enabler for real-time page numbers.

**Display**: `ReaderBottomBar` gains an optional `String? pageInfo`. `ReaderProgressBar._epubPageInfo` computes it from `currentSpreadCount`/`currentSpreadIndex`/`currentChapterPageBreaks`. PDF/scroll modes pass null → bottom bar falls back to the percentage.

## Architecture Decisions

### A1: Engine-layer rendering (not reader_body-layer)

Dual-page rendering lives in `EpubxRenderer._buildPaged`, NOT in reader_body. Reason: Paginator measurement, PageController, HtmlSlicer, and highlight injection are all engine-layer; dual-page must coordinate with all of them. reader_body only flips the `dualPageMode` flag via `setDualPageMode` based on width.

### A2: dualPageMode as private field + setter (not public mutable)

`_dualPageMode` is private; access via `dualPageMode` getter; mutation via `setDualPageMode(value)`. The setter clears `_cachedBreaks`, does `jumpToPage(0)`, and emits `ReaderEngineReady`. This guarantees that on toggle: cache invalidates (new width → new break count), page index resets (avoids out-of-bounds vs new itemCount), and the widget tree rebuilds (picks up the new rendering branch). A bare public field would miss these side effects.

### A3: spreadCount as the single source of truth for chapter-end / last-page logic

`_maybeEmitChapterEnd`, `nextPage`, `previousPage`, and `_maybeApplyPendingLastPageJump` all use `currentSpreadCount` (not `breaks.length`) for thresholds. In single-page mode `currentSpreadCount == breaks.length`, so behavior is unchanged. In dual-page mode, `_pageController.page` is a spread index (PageView's itemCount = spreadCount), so all thresholds must use spread count.

### A4: Three-layer defense for Bug #1 (no single point of failure)

Bookmark red screen had multiple contributing factors (post-frame callback outside try-catch, missing bounds guards, missing jumpToPage(0)). Rather than betting on one fix, all three are applied. If the user still reproduces a red screen, the stack trace will pinpoint which layer remains leaky.

## Risks

1. **Measurement-vs-render height mismatch grows in dual mode** — Paginator measures plain text at half-width; HtmlWidget renders rich HTML at half-width (more line wraps). Error was <1 line in single mode; may grow. Accepted; M3 may switch measurement to HtmlWidget.
2. **Cross-page text selection in dual mode** — SelectableRegion stays active (unlike PDF which disables it). Cross-page selection may attribute text to the wrong page. Deferred until user reports.
3. **Window resize single↔dual toggle** — cache key includes viewport Size (auto-invalidates on halving), and `setDualPageMode` resets page to 0. Low risk.
4. **Bug #1 may still reproduce via an untraced path** — three-layer defense applied, but without the user's yellow stack trace, can't be 100% certain all paths are covered. If it recurs, the stack trace will identify the remaining gap.
