## 1. Context（为什么做）

### 1.1 用户实测反馈（2026-07-05 21:30，附 zhiyue_pdf.log）

> 1. markdown 回到了最开始的问题：双页正常、分句正常，但**分段乱**：第一段在左页上方，第二段在右下下方超出底线，第三段在下一双页左下超出底线。
> 2. PDF **一张都没加载成功**。
> 3. PDF 加载没成功关闭软件后，**不能再次开启**，老进程依旧在，是不是被 PDF 拖累。

### 1.2 日志铁证（`zhiyue_pdf.log` 关键时间线）

```
21:25:27.145  openFile success: pages=134              ← PDF 文档解析成功（29MB）
21:25:27.239  onViewerReady(LEFT): goToPage(49)        ← 左 controller ready
21:25:27.261  onViewerReady(RIGHT): goToPage(50)       ← 右 controller ready
21:25:31–33   _goToDualPageSpread(leftIdx=0) × 30+ 次  ← 异常密集调用（每秒 15+ 次）
21:25:39.891  dispose start: doc=true                 ← 用户关窗
（之后）       （没有 dispose done）                    ← _doc.dispose() 永远不返回
```

### 1.3 根因（基于日志 + pdfrx 源码调研）

**PDF 死锁根因**：当前双页实现 `_buildDualPage` 用了**两个独立的 `PdfViewer.data()`**，靠 `sourceName` 加 `#L`/`#R` 后缀让 pdfrx 当成两份文档加载。后果：
- 同一份 29MB PDF 被 pdfium 加载两次，内存翻倍（日志显示 RSS 620MB → 656MB）
- 两个 `_PdfViewerState` 各自维护渲染队列，密集 `goToPage` 时队列堆积
- `_PdfDocumentListenable` 在 widget dispose 时才释放内部 `_document`，而我们 `_doc.dispose()` 只 dispose 自己持有的那份 → pdfium 内部仍持有文档引用 → `FPDF_CloseDocument` 等待内部渲染线程 → **死锁**
- 进程不退出 → 持有 named mutex → 第二次双击 exe 起不来（**问题 3 的真因**）

**MD 分段根因**：MD/TXT 当前复用 EPUB 的纯文本机械分页器（`Paginator`），它按 TextPainter 测量把"连续字符流"切成等高页。MD 转 HTML 后用 `_forceVisibleLineBreaks` 给每行加双空格强制 `<br>`，**打破了"连续字符流"假设**——Paginator 在 `<br>` 处的测量与实际渲染高度不一致，导致段落被切到页面中间、内容溢出页面边界。

### 1.4 为什么不再打补丁

- PDF 死锁：M4.6-fix4 ~ fix8 共 5 次失败
- MD 分段：M4.6-fix2/3/5/7 共 4 次失败
- systematic-debugging 铁律：**3 次以上失败 = 当前架构错误，必须停止打补丁，重写架构**
- 用户原话："是不是 markdown 和 txt 按 epub 方式加载的问题，不行就单独设计管线" —— 用户已独立得出架构错误的结论

## 2. Goals

### G1. PDF 双页重写（方案 A：单 PdfViewer + 副页预览）
- **G1.1** 主区用**单个** `PdfViewer.data()`（单 PdfDocument），副页用 `PdfPage.render()` 渲染下一页位图
- **G1.2** `_doc.dispose()` 必须**在 5 秒内返回**（日志验证 `dispose done`）
- **G1.3** exe 双击 → 关闭 → 再次双击**能正常启动**（无僵尸进程残留）
- **G1.4** PDF 文件能正常加载并翻页，不再"一张都加载不出"

### G2. Markdown 独立管线
- **G2.1** MD 不再走 EPUB 的 `Paginator`，强制走 `PaginationMode.scroll`（既有 `_buildScroll` 分支）
- **G2.2** MD 段落完整呈现，**不被切断**、**不溢出页面边界**
- **G2.3** MD 段内每行保留可见换行（`_forceVisibleLineBreaks` 行为保留）
- **G2.4** MD **不做双页**（单列滚动；fwfh 不支持 CSS column-count，双栏需自定义 RenderObject，收益低）

### G3. 兼容性
- **G3.1** EPUB 渲染零改动（已有的 EPUB/PDF 双页、高亮、目录、进度条全部不回归）
- **G3.2** 现有测试不回归（`pdf_renderer_test`、`pdf_renderer_dual_page_test`、`markdown_book_loader_visible_breaks_test` 全过）

## 4. 方案选型（Architecture Decisions）

### A1. PDF 双页：单 PdfViewer + 副页 `PdfPage.render()` 位图

**决策**：采用方案 A，否决"两个 PdfViewer"和"完全自渲染"。

**否决理由**：
- **两个 PdfViewer**（当前实现）：死锁根因，已用日志证明
- **完全自渲染**（方案 B）：要重写文本选择、缩放、高亮、滚动惯性，工作量 1-2 天，且 pdfium 密集翻页仍可能卡
- **换 PDF 包**（方案 C）：syncfusion 体积大、pdfx 维护停滞，不确定性高

**方案 A 细节**：
```
┌─────────────────────────────────────────┐
│  Row                                     │
│  ┌──────────────┐  ┌──────────────┐    │
│  │ Expanded     │  │ Expanded     │    │
│  │  PdfViewer   │  │  CustomPaint │    │
│  │  .data(      │  │  (副页位图)  │    │
│  │   bytes,     │  │              │    │
│  │   controller)│  │              │    │
│  │  ← 主页      │  │  ← 副页      │    │
│  └──────────────┘  └──────────────┘    │
└─────────────────────────────────────────┘
```
- 主区：单个 `PdfViewer.data(bytes, controller: _mainController)`，显示当前页（偶数索引）
- 副区：`FutureBuilder<PdfImage?>` + `CustomPaint`，在 `_currentPage` 变化时调 `doc.pages[rightIdx].render()` 生成副页位图
- 翻页：`previousSpine`/`nextSpine` 仍 step=2，setPage 更新 `_currentPage` → 主 viewer `goToPage` + 副页重新 render
- 文本选择/高亮：仅主页支持（与现状一致，双页下选择禁用）

**为什么不死锁**：
- 只有**一个** `PdfDocument`，`_doc.dispose()` 是唯一释放点
- 副页位图用 `PdfPage.render()` 同步获取 `PdfImage`，渲染完立即 `dispose()`（不持有页引用）
- 不再有第二个 `PdfViewer` widget，dispose 路径干净

### A2. PDF dispose 安全网：dispose 超时强制继续

**决策**：在 `dispose()` 里给 `_doc.dispose()` 加 3 秒 `timeout`，超时则 catch `TimeoutException` 继续往下走（关闭 stream）。即使 pdfium 内部卡死，Dart 侧 dispose 也能返回，不阻塞进程退出。

```dart
Future<void> dispose() async {
  pdfDiagLog('dispose start');
  _memMonitor?.cancel();
  try {
    await _doc?.dispose().timeout(const Duration(seconds: 3));
  } catch (e) {
    pdfDiagLog('dispose timeout/error (ignored): $e');
  }
  // ... close streams ...
  pdfDiagLog('dispose done');
}
```

**注意**：这是**安全网**，不是主要修复。主要修复是 A1（单 PdfDocument）。安全网确保即使未来出现新卡死，exe 也能退出。

### A3. Markdown 独立管线：HtmlWidget 滚动渲染（scroll 模式）

**决策**：MD 强制走 `PaginationMode.scroll`（既有 `_buildScroll` 分支，零新渲染代码），跳过 EPUB 的 `Paginator`。**MD 不做双页**（单列滚动）。

**否决其他方案的理由**：
- **paged 模式 + 修 Paginator 加段落感知**：Paginator 假设深（按 plain text 偏移机械切页），改它风险大、已失败 4 次（fix2/3/5/7），容易回归 EPUB 自身分页。
- **scroll 模式 + CSS column-count 双栏**：调研确认 fwfh 0.15.2 的 `Column` 是 widget 纵向排列，**不支持** CSS `column-count` 多栏报纸排版。要实现双栏需自定义 `RenderObject`，复杂度高、收益低。
- **scroll 模式 + Row(Expanded, Expanded) 同章两份 HTML**：fwfh 渲染整章是单列流式，无法把同一章内容自然分到左右两栏（要么重复渲染、要么裁切，两者都破坏阅读体验）。

**为什么 MD 不要双页可接受**：
- 用户原话："**TXT 看起来是正常的**"——TXT 保持 paged+双页不变。
- 用户原话："**只有 markdown 出现了问题，如果确定改不好，就只重写 markdown**"——优先级是"段落不溢出/不切断"，双页是次要。
- MD 内容通常是技术文档/笔记，单列滚动阅读完全可接受（GitHub、VS Code 预览都是单列滚动）。

**实现**（极简，复用既有代码路径）：
1. `reader_engine_provider.dart`：MD 路由在 `openChapters` 后**调一次** `engine.setPaginationMode(PaginationMode.scroll)`（fix5 删掉了这个调用，fix9 加回来，但**只对 MD**，TXT 不调）。
2. `_buildScroll` 已存在（`epubx_renderer.dart:995`），用 `SingleChildScrollView + HtmlWidget` 渲染整章，段落完整、不溢出。
3. `_forceVisibleLineBreaks`（fix7）保留——段内每行换行仍生效（`<br>` 在 scroll 模式下正常渲染）。
4. `reader_body.dart:393` 的双页 gate：MD 走 scroll 后 `paginationMode != paged`，自动跳过 `setDualPageMode`（既有逻辑，零改动）。

**为什么解决问题**：
- `HtmlWidget` 按段落原生布局，**不会把段落切到页中**
- `SingleChildScrollView` 内容自适应高度，**不会溢出边界**
- 段内换行由 `<br>` 保留（fix7 测试通过）

**对 TXT 的影响**：零。TXT 仍走 `ConcreteEpubReaderEngine.openChapters` 但**不调** `setPaginationMode(scroll)`，保持默认 `paged` + 双页。MD/TXT 在 provider 里按 `bookRef.format` 分流。

### A4. exe 僵尸进程防御：保留 fix4/fifix6 的 ExitProcess + 互斥锁接管

**决策**：不动 `main.cpp` 的单实例逻辑。A1 修复 PDF 死锁后，进程能正常退出，互斥锁自然释放。fix4/fifix6 的 ExitProcess + 接管逻辑作为最后防线保留。

## 5. Risks

### R1. 副页 `PdfPage.render()` 在大页（如 A1 图纸）时渲染慢
**缓解**：副页用 `limitedImageCache` flag + 较低分辨率（`fullWidth` 限制为容器宽度 × devicePixelRatio），渲染超过 2 秒显示"加载中"占位。

### R2. MD 无双页可能不符合用户潜在期望
**缓解**：用户明确说"TXT 正常，只改 markdown"——优先级是段落不溢出。MD 双页需求较弱（技术文档单列阅读可接受）。若后续用户反馈强烈，再做专门的双栏 RenderObject（v1.5.2+）。

### R3. fwfh `HtmlWidget` 与 EPUB 的 `flutter_widget_from_html_core` 版本冲突
**缓解**：项目已用 fwfh 渲染 EPUB 章节 HTML，MD 复用同一依赖，无新冲突。

### R4. 测试覆盖
**缓解**：
- `pdf_renderer_test.dart` 加 dispose 超时测试
- `markdown_book_loader_visible_breaks_test.dart` 保留（验证 `_forceVisibleLineBreaks` 不回归）
- 新增 `markdown_pipeline_test.dart` 验证 MD 走新管线（不走 Paginator）

## 7. 三件套防御回顾（fix9 是第 9 次尝试，必须可追溯）

本次修复针对的是**反复失败的 PDF 死锁和 MD 分段**，每次失败的根因和教训必须在 CHANGELOG 的 Lessons 段记录，确保下次回归时能快速定位：

| 失败轮次 | 假设 | 实际 | 教训 |
|----------|------|------|------|
| fix4 | ExitProcess 解决僵尸 | PDF 死锁未解，进程仍挂 | 死锁源在 Dart 侧 dispose，不在 C++ 侧 |
| fix6 | 互斥锁接管解决二次启动 | PDF 死锁未解，接管无效 | 接管只能处理"已死"互斥锁，不能让活进程退出 |

| **fix9** | **单 PdfViewer 根除死锁** | **（待验证）** | **架构对了，死锁应消失** |
